# Establish a project

Read for setup: this file, `identity.md`, `templates/profile.md`, `templates/setup.md` and `config.default.json`. Consult `POLICY.md`, `SCHEMA.md` and the other procedures only when a rule is unclear or a step points to them; do not load them up front.

Default timebox: two working days. Use `templates/setup.md`; record actual time and usage per step, or unknown. Start in assisted mode. If the timebox is insufficient, the owner explicitly narrows supported scope or extends it. Do not label incomplete controls operational.

## Who does what

Each step is tagged **script**, **agent** or **owner**. The agent performs the script step and the agent steps, writes the owner steps into the setup record as a checklist stating what each needs, posts that, and stops. It never attempts, retries or waits on an owner step, and never asks for credentials, keys or protection changes to be handed to it. Owner steps need the owner's accounts and cannot be delegated. `bin/wf-adopt` performs the script step and writes the checklist.

## Two starting points, one set of controls

**New project:** the script step, the agent steps, then the owner checklist. The first milestone is the observed pilot (step 11).

**Existing repository:** the same controls in the same order, with three rules that keep the cost bounded. Do not inventory the codebase: fill the profile's *Starting position* and *Technical context* from what the owner says and from the README, manifests and directory listing, and leave the rest under *Unknowns* with the stage at which each becomes required; the codebase is learned per task. Classification is a config edit, not a survey: `wf ci` classifies only the paths a candidate changes, and `config.default.json` already covers common source; add the stack's missing patterns (for example `**/*.{dart,vue,svelte}`, `Cargo.toml`, `requirements.txt`) and stop. Keep the first milestone small enough to serve as the pilot. Porting the code into a fresh repository under the owner account is an option the owner may choose when the old repository's protections, collaborators or CI are hard to verify; it simplifies the owner steps and none of the agent steps, and it loses GitHub-side history and integrations. Record the choice in the setup record.

## Steps

1. **[agent]** Create the profile and brief from the owner's input, including anything in `docs/workflow/inbox/`. Define source precedence, users, outcomes, scope, exclusions, journeys/data, risks, decisions, verification and delivery. Record unknowns with a required-before stage. Preserve distinctions between approved requirements, prototypes, historical records and derived indexes.
2. **[owner]** Verify the personal GitHub owner username; create/retain the repository there. Verify the development worker username independently. Configure separate human and agent clones and follow `identity.md`. Do not switch global accounts. Worktrees isolate concurrent work only.
3. **[script]** Adopt an immutable workflow tag and commit: `bin/wf-adopt` writes `docs/workflow/config.json` with the tag and full hash, the record directories, the profile, setup and acceptance seeds, the local launcher, the `AGENTS.md` / `CLAUDE.md` adapters and `.github/workflows/wf-status.yml` when absent, and fetches the pinned installation. That workflow republishes `wf status` with the open pull requests to a *Project status* issue after each push to the trusted branch, and every six hours when that is the default branch. It is a convenience view that approves nothing and that a collaborator's own workflow could also edit, so check consequential items against the records and pull requests; it is public on a public repository. A trusted branch other than `main` is set in both `docs/workflow/config.json` and that file; delete the file to opt out. Keep active milestones on their adopted version until explicitly upgraded.
4. **[agent]** Classify by effect what the defaults miss for this stack: migrations, scripts, dependency/configuration files, infrastructure and generated inputs/outputs. Approval records and enforcement surfaces are protected by the defaults; keep them so. Unclassified changed paths block integration. External skills/tools require inspection of instructions/scripts/permissions/dependencies, a pinned version, representative testing and a toolbox record before adoption.
5. **[owner]** Establish owner-controlled bootstrap, then record when normal protections become active. Protect approved requirements, acceptance definitions, decisions, workflow configuration, validators, runners, CI, and CODEOWNERS. Require owner review, stale-review invalidation, administrators subject to restrictions, no worker bypass, and trusted checks bound to their producing application. Make `wf ci` and every entry of the profile's `required_checks` a required status check, adding each entry when approving the profile change that defines or changes the list, and require branches to be up to date before merging, so the integration rerun (POLICY § 9, layer 3) runs on the assembled candidate and a failing check blocks the merge even after approval. Verify check provenance and the protected CI entry point, not only its name. Check GitHub plan support and record unavailable controls. Pin the *Project status* issue once the status workflow has opened it.
6. **[owner]** Choose the approval mode and provision what it needs (`approval-evidence.md`). **Enforced**, the default recommendation: once step 5's protections are verified and step 9's approval-path test has passed, set `approval.label` in `docs/workflow/config.json` and `approval_label` in the profile to `enforced` in one code-owner-reviewed pull request; the fetched authoritative branch is then the approved baseline, no signing key is needed, and the checker lists receipt-dependent evidence as `unverified` for the pull request review. **Manual signed receipts** when the repository cannot be protected: provision the owner public key outside the agent clone and sign receipts per candidate. In both modes install the launcher outside candidate control for authoritative runs and bind its full revision in protected runner configuration; local copied launchers only provide feedback; the required check must run the pinned validator from the protected CI entry point, with its result tied to the exact candidate; candidate tests run separately without owner credentials or signing keys.
7. **[agent]** Define the profile's `required_checks`: the stack's applicable type, build, lint, component-boundary and test commands, named as CI reports them, or the recorded reason one does not apply; readiness fails while the list is empty. Define acceptance IDs and methods in `docs/workflow/acceptance.json` and mappings in `tests/acceptance-map.json` for the first milestone only. Capture actual reporter output, environment, revision, and limitations. In manual mode the owner-controlled collector verifies provenance and signs receipts after examining raw evidence; in enforced mode the evidence is posted on the pull request for the code-owner review. No candidate `passed` field supplies evidence by itself.
8. **[agent, own session]** Run the gate, acceptance, identity and session fixtures. Test tool instruction discovery in a fresh Codex session and a fresh Claude Code session: ask each to identify governing policy, ready work, pending authority, and its permitted next action; then give a blocked task and confirm no production edit. Record actual tool version, prompt, transcript and result. Reading the adapter files alone is not a discovery test. Do this in its own session, not the one that wrote the profile.
9. **[owner]** Run a real approval-path test in an authorised disposable branch/repository: worker direct push and unapproved protected change must be rejected; owner approval plus authentic checks permits the intended change; stale approval becomes invalid. Also record what bringing an approved branch up to date with the base does (which checks rerun, whether the approval is dismissed); with up-to-date branches required, it happens after every merge. Do not probe a production branch destructively. Record requested action, observed rejection/acceptance and resulting revision. When it passes, complete the switch to `enforced` from step 6.
10. **[owner, then agent]** For central feedback, provision the external operations config and private runtime directory using `operations.md`. Record the owner-authorised public data boundary and issue worker. Then test actual instruction discovery and reporter calls from both Codex and Claude Code, plus wrong/missing identity and unknown delivery. Do not claim least privilege from one successful issue write.
11. **[owner and agent]** Pilot a small authorised milestone under observation. Record technical and workflow outcomes separately using `templates/pilot.md`. Verify review, integration and acceptance before considering unattended execution.

## Stop rule for the agent

The agent's setup work is its steps only, one session at a time, and half a working day of its own wall-clock time in total unless the owner records another allowance in the setup record. At the end of each session it records in the setup record what each step consumed (time and usage, or unknown), the owner checklist and the next agent step, posts that, and stops; the next session continues from the record. Setup in one long session with no stop is what exhausts an allowance.

The runner is **not adopted** in this implementation. Unattended mode requires a separately approved runner, duplicate-claim prevention, persistent cumulative budgets, bounded calls/retries, child-process cleanup, interrupted-action recovery, a pause proven by observed silence rather than by a stop instruction, and all runner fixtures plus a pilot. Graphify and other generated navigation tools remain deferred optional tools, not missing prerequisites.
