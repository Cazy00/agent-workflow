# Independent review and integration

Prepare a committed candidate plus scope, task/milestone records, governing requirements and acceptance definitions, relevant designs, exact base/candidate diff, verification evidence and limitations. Use `wf review-packet --baseline SHA --candidate SHA --task T-NNNN --evidence /external/checks.log` to prepare fixed canonical references from a clean checkout, and rerun it after review to detect changes. It grants no approval. Launch a separate review context without the implementer's conversation or informal reasoning: a harness subagent with an explicitly empty starting context or a fresh session. For Codex, set `fork_turns: "none"` explicitly; omission inherits conversation in some harness versions. For Claude Code use a fresh reviewer context, never resume the implementation collaborator. Record the actual launch options/context metadata and candidate SHA with the returned review. A separate agent ID or a `separate_context` assertion alone does not establish independence. The coordinator's prompt names the candidate revision, diff base, task and milestone records, governing requirements, acceptance definitions, designs, verification evidence and limitations, by path or revision, and asks for `templates/review.md` filled in with findings, severity and disposition. It does not paste the coordinator's own conclusions. In Claude Code the `independent-reviewer` subagent that `wf-adopt` installs at `.claude/agents/independent-reviewer.md` is that context; in Codex or Cursor register the same prompt as a custom agent before first use and record it in the toolbox. The reviewer has shell access to run the checks; its instruction not to modify the candidate is a prompt, not an enforcement, so review a committed revision and compare it afterwards. The owner does not run reviews; the owner sees the posted result. Canonical design rationale remains available.

**Levels.** Each review has a level, stated in its evidence (`review.level`). Every level but `none` is reviewed by a model from another vendor than the implementer's (POLICY, *Independent review*):
- `none`: a test-only change. Every production path it changes is a test path (in a `test/`, `tests/` or `__tests__/` folder, or a test file by its language's convention), none is an owner-approved acceptance test and none is deep. It needs no review; verification and integration evidence still apply, and `wf ci` notes it (MAINT-0021).
- `light`: copy, styling, one component or a small internal tool, at the `cheap` reviewer role. It looks at the change and what directly uses it.
- `standard`, the default: a feature inside one area, at the `standard` role, adding its callers and the records for that area.
- `deep`: permissions, money, migrations, sign-in, deleting data, and the project's `review.deep_paths`, at the `strong` role, with a security focus. It looks at the change with the code it affects. `wf ci` fails a change to a deep path without one. A deep glob that matches by name anywhere (`**/*numbering*`) reaches a test file (SCHEMA.md says which count) only when it names tests; a glob anchored on a folder reaches everything under it. A test-only change to code a name glob marks deep is reviewed at its own level.

**Who reviews.** With `review.reviewer_command`, one command picks the reviewer for every level: the briefs print it with `{role}` filled in (light `cheap`, standard `standard`, deep `strong`, a fix check `fixcheck`, the milestone `milestone`), and the command chooses the model and its effort, so no one asks the owner which to use. Without it, `review.second_model` reviews. By the owner's decision of 17 October 2026, a task's review uses its `model` at high effort (at most `max_effort`), and only the milestone review, the one last check of everything built, may use `final_model` at `final_effort`, to conserve the second model's usage; `wf ci` refuses a task's review by it. Pass the effort explicitly, as `wf brief` prints it, since Codex's default is low. A reviewer is launched detached from the agent's process, its output to a file (`setsid` or `nohup`), so a restart of the session does not kill it. The reviewer is never of the implementer's vendor: record `review.vendor` and `review.implementer_vendor`, which `wf ci` refuses when they are the same, and the implementer's and the reviewer's models. The implementer's self-review, and reviews by subagents of its own tool, are optional and never count as the review. If a reviewer cannot run: relaunch it once after a transport error, take the next model after a quota error, and otherwise record the review as missing and stop at the gate; there is no fallback to the implementer's own tool.

**Severity.** The reviewer sets it, never the coordinator, in three words. **Blocking:** a user or the owner would hit wrong behaviour, or there is a security hole, a way to lose data, or a gate that can be bypassed; it states its exposure (what can go wrong, for whom, shown by the reproduction), and a request the server refuses, or a gap no person can reach, is not blocking. **Should fix:** real, with low impact; it is fixed in the same change without another review, or becomes a found task when larger. **Note:** style, wording or ideas; it never starts anything. Putting a governing file back to the trusted branch's content leaves the review standing (`lib/carry.js`). A blocking finding in code the pull request does not change, whose exposure its merge does not increase, may be carried by a found task whose `found_from` names it: give the finding `carried_by`, `paths` and `merge_increases_exposure: false` and list it in `accepted_findings`, and with `approval.defer_to_acceptance` the agent still merges (POLICY, *Approval evidence*). Any other blocking finding waits for the owner.

**How many.** A change is reviewed once, on its final code. After the fixes, a light or standard change gets nothing more, and each blocking fix comes with a test that failed without it. A deep change and the milestone get one **fix check**, and only after a blocking finding: a new fresh-context reviewer at the `fixcheck` role, given only the earlier findings, the fix diff and the tests added, answering for each finding fixed, half-fixed or fix broke, and adding at most one finding the fix itself introduced. There is no round three: a problem still left after the fix check is fixed, proven by a test and recorded in the pull request, and a further check runs only if the owner asks. Where a fix check leaves only a non-blocking residual, accept it with its resolution, list it in `accepted_findings` and carry it to a later milestone; with `approval.defer_to_acceptance` the owner sees it at acceptance, otherwise in the merge, as any accepted finding. Review and verification carry over a merge of the trusted branch or a records commit: `wf ci` checks that every path changed since is a planning record, or one the pull request had not touched that now holds the trusted branch's content, or a governing file put back to the trusted branch's content. Anything else needs a new review. The milestone gets one review of its whole diff before acceptance (`accept-release.md`). Budget, which `wf next` prints: with `review.reviewer_command`, one run per light or standard task, two per deep task (its review and one fix check), none for a test-only task, and two for the milestone; with `review.second_model` alone, two per deep task and one for the milestone. Before a run, `wf usage --milestone M-NNNN --since AUTHORISED_AT` counts the runs used since the milestone's authorisation against its budget (`wf brief --acceptance` prints how to find that time).

Run the reviewer in the foreground and collect its result in the same turn (in Claude Code, `run_in_background: false`; its subagents default to the background), and follow `execute.md` on background work: in the pilot the coordinator stopped to wait three times and the owner had to wake it. A fix check is a new fresh-context reviewer given the earlier review and the fix diff: resuming the earlier one carries its history and may run in the background. If a reviewer ends in an API or transport error, relaunch it once; after a second failure take the next model, and with none left record the review as missing and stop at the gate. A network outage cost the pilot a review and an owner prompt.

Review scope, correctness, maintainability, security, regression risk and test fidelity. Look for the failure patterns most often missed in agent-written code: errors caught and silenced, fallbacks that hide a failed call, dependencies added that are unused or do not exist, logic duplicated where the codebase already has it, behaviour beyond the task's scope, tests weakened to pass, a change that crosses a component boundary or breaks a convention the profile's *Technical context* records, and secrets or environment-specific values in code. When a finding category recurs, turn it into a mechanical check (a lint or boundary rule, a test) through a normal task and add it to `required_checks`, instead of relying on review to catch it again; when approving that profile change, the owner adds it to the ruleset's required status checks (setup step 5). Inspect supporting helpers, fixtures, setup, assertions, execution configuration and untagged tests. Mapping IDs prove traceability, not quality. A blocking correctness or security finding comes with a failing test, an exploit or exact reproduction steps where one can be written, so its fix can be shown to work; one that cannot says why and is weighed as judgement. Post candidate identity, reviewer/context, checks, findings with category/severity/disposition and reproduction, the owner summary, evidence and limits on the pull request using `templates/review.md`. Collect the actual separate-context result; the implementer cannot substitute `reviewed: true`.

New tests for approved behaviour are normal implementation. Explain meaningful test refactors. Correct tests contradicting approved requirements by citing the requirement and independently checking the correction. Approved behaviour changes need a focused requirement/decision approval present on the authoritative baseline first. Removed/disabled/weakened required coverage blocks integration until justified through the correct route; a linked spec PR or candidate approved field is insufficient.

For a renamed required test, place its exact old/new mapping pair, current task ID and governing requirement in the authoritative baseline's `docs/workflow/acceptance.json` `mapping_migrations` before relying on it. The candidate's own declaration grants nothing. Confirm the replacement still tests the approved behaviour, that no unrelated mapping was removed, and that the new test ran once and passed; in enforced mode, record execution and coverage as unverified by the validator; the agents remain responsible for checking them. The validator checks exact traceability, not semantic equivalence. All test code changes require semantic review; the adverse cases in `validator/test/acceptance.test.js` guard the migration boundary.

After review, assemble the candidate with the latest authoritative baseline and rerun required integration checks. Revalidate approval, readiness, paths, coverage and review at that exact candidate. Capture verification/execution and review through the owner-controlled receipt procedure. Keep candidate code in a separate unprivileged environment. Invoke the external trusted validator with explicit baseline/candidate; never execute a candidate-selected validator or accept a check name as proof of provenance.

Planning, checkpoints and feedback remain possible while production is blocked. Generated outputs conservatively receive production gates. Protected governing/enforcement changes need scoped signed receipts; dependent implementation still reads requirements/decisions from the earlier approved baseline, so a combined proposal does not approve itself.
