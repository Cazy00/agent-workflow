# Changelog

Releases are tags, and the host's release broker makes them (`wf-release`; from v2.19.0). After one deep review of the commit that sets the version in `package.json`, the broker tags that commit, creates the release and moves `canary` to it; `stable` follows after a 24 h soak, once the canary project's gate and status runs have passed on it. Nobody types a tag, and no workflow in this repository tags or pushes a ref, which `validator/test/status-workflow.test.js` checks by what a workflow can do (a ref-writing step or `contents: write`), not by file name. The tag ruleset and what the broker tags and signs belong to the host and are described in its docs (the workspace repository's `broker/docs/wf-channels.md`); this repository enforces only that a channel resolves through a signed record (`bin/wf-resolve`), and checks a pin or an entry tag for shape and minimum version. Before v2.19.0 a release was tagged by `.github/workflows/release-tag.yml` when the owner merged the pull request that bumped `package.json`. A project adopts a release only by moving its pin, with `bin/wf-upgrade` from `v2.0.0`, or follows a channel (v2.19.0); a new tag never upgrades a pinned project by itself. What a project must do when it moves to a release is under that release, and `bin/wf-upgrade` lists it from `upgrades.json`.

## v2.19.4

2026-11-12. A patch for hosts that run the CI pool: a refusal of the job-started check kills the Worker even when the Worker's stderr cannot take the refusal (found by the deep reviews of #115, N2, and of home's pin PR, F2). Nothing changes for a project.

- **The write to the Worker's stderr cannot hold back the kill.** v2.19.3 wrote the refusal to `/proc/<worker>/fd/2` before the 3 s pause and the kill, with nothing bounding it: a full pipe nobody drained would block the check, the Worker would stay alive, and a later timeout or cancel could let the job's `always()` steps run. The write now runs in the background under `timeout -s KILL 1`, and the pause and the kill follow at once, whatever the write does. No account could cause the full pipe (the runner's Listener drains it), but a blocked write must not fail open.
- **Appended, not truncated** (#115 N1): the write opens fd 2 with `>>`, so a Worker whose stderr is a file keeps what it held.
- **What the fallback keeps** (#115 N3): when no Worker is found and the pool image's own check kills every process of the runner's user, the Listener ends too, so that refusal is in the job's live log only; the README and this entry say so.
- Tests (`server/ci-runner/test_ci_pool.py`): a fake `Runner.Worker` whose stderr is a pipe nobody reads, filled by a blocked writer, is still killed and runs no step; a Worker whose stderr is a file keeps its earlier text; an allowed run writes nothing to the Worker's stderr (#115 N4); the write is the backgrounded, time-bounded one and comes before the kill. A failed `/proc` read is covered only by the check having no `2>/dev/null` (#115 N5).
- Upgrade: a host reinstalls the pool and rebuilds both images.

## v2.19.3

2026-11-12. A patch for hosts that run the CI pool: a refusal of the job-started check (v2.19.2) is visible. Nothing changes for a project.

- **Which check failed, and the values it read:** besides its reason, a refusal prints a second `::error::` line with the event, `GITHUB_ACTOR`, `GITHUB_TRIGGERING_ACTOR`, `GITHUB_REPOSITORY`, and the head and base of the payload's pull request or workflow run (`not set` or `none` where there is none). Each value is shown with anything outside a login's or a repository name's characters replaced, so a value cannot start a workflow command of its own.
- **It stays on the job:** the check kills the job's `Runner.Worker`, so the step's log may never be uploaded. Before the kill it writes the same lines to the Worker's own stderr, and the runner's Listener attaches what a dying Worker printed to the failed job as an error.
- **No stderr to `/dev/null`:** jq's error on a payload it cannot parse, a list file it cannot open, and a `/proc` read that fails now reach the job's log beside the refusal.
- Tests (`server/ci-runner/test_ci_pool.py`): the context line for a fork's pull request, a fork's workflow run and missing values; a value with a newline and `::` cannot start a line; jq's parse error and a missing list's error reach stderr; the hook has no `2>/dev/null`; under a fake `Runner.Worker`, the Worker's own stderr receives the refusal before it is killed.
- Upgrade: a host reinstalls the pool and rebuilds both images.

## v2.19.2

2026-11-12. A patch for hosts that run the CI pool (`server/ci-runner`). The JIT source mints a runner only while no one outside the trusted accounts can reach one (home's broker: `repo_shared`), but a runner takes any queued job of its label, so a job queued after that check (a pull request from a fork, a re-run by another account) could still run in the container. Now the container checks the job itself, before the job's first step.

- **The job-started check** (`/opt/ci-hooks/job-started.sh`, written by `ci-pool-image` into both images; `ci-pool-entrypoint` sets `ACTIONS_RUNNER_HOOK_JOB_STARTED` to it and starts no runner in an image without it). It refuses unless `GITHUB_ACTOR` and `GITHUB_TRIGGERING_ACTOR` are trusted accounts (compared ignoring case) and a pull request in the event payload (`pull_request`, `pull_request_target`, the review and review-comment events, any payload that carries one) has `head.repo.full_name` equal to `base.repo.full_name`; a `workflow_run` payload's `head_repository` must equal its `repository`. A missing or unreadable value, and any error in the check, refuses. The runner takes these values from GitHub's job message before any code of the job has run, and the job's `env:` does not reach a hook (the README says why, from the runner's source), so they need no token: the runner gives a hook none. External commands are called by absolute path.
- **A refusal kills the job's `Runner.Worker`** (the check's parent or its parent's parent, by name and by executable; where there is none, the pool image's own check kills every process of the runner's user): a failed hook alone fails the job, but the runner still runs the later steps whose own `if:` holds (`always()`), and a fork's pull request brings its own workflow file.
- **The trusted accounts** are `ci-pool-image`'s `TRUSTED_ACTORS`, which the build checks (not empty, logins only) and writes to `/opt/ci-hooks/trusted-actors`. They must be the JIT source's own; the default is home's (the owner, the agent and the executor App's bot).
- **What changes for a project:** a pool job that `dependabot[bot]` or a workflow's own token (`github-actions[bot]`) started is refused; home's broker already minted no runner while such a run was active. Those jobs must run on GitHub's runner.
- Tests (`server/ci-runner/test_ci_pool.py`, `JobStartedCheckTests` and `EntrypointTests`): the owner's runs and own pull requests pass, case ignored; a foreign actor, a foreign re-run, look-alike logins, a pull request from a fork under each pull-request event, a fork's `workflow_run`, a missing or empty trusted list and every missing or malformed value refuse; a refusal under a process named `Runner.Worker` with the runner's executable kills it before the next step, also through a wrapping shell, and a process with the name only is not killed; the build refuses a bad `TRUSTED_ACTORS` and writes the list without glob expansion; the entrypoint passes the hook to the runner and starts none without it.
- Upgrade: a host reinstalls the pool and rebuilds both images; a host whose accounts are not home's builds with `sudo TRUSTED_ACTORS='...' ci-pool-image build wf-build` (and `wf-gate`), or every job is refused. A container from an older image runs without the check until then.

## v2.19.1

2026-11-09. A patch with three changes. First, a draft run of `wf ci` can no longer cancel the `wf ci` run of the same pull request (found by the deep review of headless-lightroom PR #120, 2026-11-08). The documented flow writes the delivery evidence into the description and then runs `gh pr ready`, which fires `edited` (draft payload) and `ready_for_review` (ready payload) moments apart. Both runs shared the group `wf-ci-<pr>` with `cancel-in-progress`, so a draft run queued second cancelled the `wf ci` run, and the head's latest `wf ci` was cancelled: it failed closed, but the pull request stayed blocked until someone reran it.

- **The group now includes the draft state:** `wf-ci-<pr or ref>-${{ github.event.pull_request.draft && 'draft' || 'gate' }}`, in `templates/github/wf-ci.yml` and `templates/github/channel/wf-ci.yml`. It reads the field the job's `name` reads, so a run named `wf ci (draft)` is always in a `-draft` group and a run named `wf ci` in a `-gate` group; a draft run can cancel only older draft runs. A ready or later run still supersedes the older runs of its pull request, and pull requests stay apart. Schedule, dispatch and `repository_dispatch` runs have no draft payload and join `-gate` as before.
- **What changes for `converted_to_draft`:** its run (a draft payload) is in the `-draft` group, so it no longer cancels a ready run still running or queued. That run can finish and post `wf ci` on what is now a draft; GitHub refuses to merge a draft, and `gh pr ready` fires `ready_for_review`, which runs the gate again and supersedes it. The headers of both templates say so. The alternative, putting `converted_to_draft` in the gate group, would let a draft payload cancel `wf ci` again.
- Tests: `validator/test/wf-ci-concurrency.test.js` evaluates each template's own `group:` and job `name:` for every pull-request event, ready and draft: a draft run's group never equals the gate run's group for the same pull request, the group's suffix always agrees with the job's name, ready runs of one pull request share a group, other pull requests and non-pull-request runs stay apart.
- **Cost:** a draft run is no longer cancelled by the ready run that follows it, so the documented flow (evidence into the description, then `gh pr ready`) runs a full `wf ci (draft)` job as well as `wf ci` on every task. On GitHub-hosted runners that doubles the minutes of that step; on a project with one `wf-gate` runner (`WF_GATE=on`), `wf ci` waits behind the draft job, up to its 10-minute timeout, but not behind the draft run's `record` job, which runs on a GitHub-hosted runner (below).

Second, the thin callers and their entries, hardened (the deep review of headless-lightroom PR #121's opt-in to the channel, receipt rv2ba4475b4695e7f0, 2026-11-08):

- **A run that is not a pull request judges only the trusted branch, in the caller too (F1):** `templates/github/channel/wf-ci.yml`'s job has `if: github.event_name == 'pull_request' || (github.ref == 'refs/heads/__TRUSTED_BRANCH__' && (github.event_name != 'schedule' || vars.WF_GATE == 'on'))`, so a `workflow_dispatch`, schedule or `repository_dispatch` run on any other ref is skipped before the entry is called. The entry's first step still refuses any ref but exactly `refs/heads/<trusted>`: GitHub compares strings in `if:` ignoring case, so the caller alone lets `refs/heads/MAIN` through.
- **`checks: write` only where the record is posted (F2):** a called workflow's jobs can only narrow what the caller grants, so each entry narrows per job. `wf-gate.yml`'s `gate` job, which runs the resolved revision's `bin/wf-gate-ci` and validator, has `contents: read` only; `wf-status.yml`'s `status` job has `contents: read`, `issues: write`, `pull-requests: read`. Their step "Prepare the record of what judged" writes the check run's JSON as the job output `check_run` before any code of the resolved revision runs, and a new `record` job (`needs` that job, `if: !cancelled()` and an output, `permissions: checks: write`, one `gh api` step, no checkout) posts `wf resolved`; the record job always runs on `ubuntu-latest`, a GitHub-hosted runner, never on the project's `wf-gate` runner. Code the channel picks can no longer post a check run such as a fake `test` or `wf ci`. The callers still grant `checks: write` (and say it is for the record job), because GitHub narrows from what the caller grants. New check names: `wf ci / record` and `wf-status / record`; `wf ci / gate` is unchanged. The record job is not on the gate runner because a `wf-gate` runner is persistent: a process the resolved revision's code leaves behind (one that escapes the runner's orphan cleanup) could read the `checks: write` token of the next job on that runner from `/proc` and post a fake `test` or `wf ci / gate` check run. A fresh VM has no such process.
- **Cost of the record job:** about one GitHub-hosted minute per run (a fresh VM, one API call, billed to a whole minute), on every gate and status run that judges, drafts and scheduled runs included, also for a project whose judging runs all on its own `wf-gate` runner and used no hosted minutes before; a scheduled run skipped without `WF_GATE` (below) costs none. A failure of the job (for instance no minutes left) fails only the unrequired check `wf ci / record` or `wf-status / record` and leaves `wf ci / gate` as it was; the `wf resolved` check run is then missing.
- **Channel projects still on the v2.19.0 entry (F5):** a project whose caller names `wf-gate.yml@v2.19.0` keeps the old shape, where the judging job holds `checks: write`, until its callers name a newer release's entry. `wf ci` still accepts the v2.19.0 entry, so `wf ci` does not tell such a project; the host's merge gate does, and `bin/wf-upgrade` moves the callers (the third change, below).
- **`wf-status` runs only on the trusted branch again (F3):** its caller's job has the copied `wf-status.yml`'s guard, `if: github.ref == 'refs/heads/__TRUSTED_BRANCH__' && (github.event_name != 'schedule' || vars.WF_GATE == 'on')`. The status entry already refused other refs twice, its job `if:` (`github.ref == format('refs/heads/{0}', inputs.trusted_branch)`) and its first step's exact `$GITHUB_REF` comparison; both stay.
- **The schedule spends no GitHub-hosted minutes without the gate runner (F8, MAINT-0023):** both callers skip a scheduled run unless `vars.WF_GATE == 'on'`, and both entries' judging jobs repeat it in their `if:` for a caller that lacks it. `repository_dispatch` from the release broker after a channel move still runs and keeps a canary's soak fresh.
- **What the entry tag's trust rests on (F4, documented):** the tag ruleset `harbor-wf-tags`, which forbids updating, deleting or force-pushing any `v*` tag (only repository admins bypass it); the release, authored by the broker's executor, which tags `main`'s head; and the host's merge gate, which checks at merge time that a project's caller is the release's own blob naming that release's tag. The caller's header says so.
- `bin/wf-gate-ci` reads only the caller's `uses:` and `entry:` lines, so it accepts the new caller and still accepts the v2.19.0 shape; asking a channel project for the new blob is the host's merge gate's job, not `wf ci`'s.
- Tests (`validator/test/gate-entry.test.js`): each caller's and entry's `if:` is evaluated, ignoring case as GitHub does, for every trigger on the trusted branch, other branches, a tag and with `WF_GATE` on and off; the entries' refusal steps run against `refs/heads/MAIN` and others; only the `record` job of each entry has `checks`, the judging job has exactly its read permissions, the record job checks out and runs nothing and always runs on `ubuntu-latest`, never on the gate runner; the prepare step's output is one line of the check run's JSON; `wf-gate-ci` accepts both caller shapes.

Third, `bin/wf-upgrade` moves a channel project's thin callers, which no command moved before (the deep review of the v2.19.1 release pull request, #109, receipt rvd7e52809f1776fa7). The channel moves the shared gate, not a project's callers, and the entries' permission split reaches only callers that name a newer tag.

- **`bin/wf-upgrade --project PATH [--rev vX.Y.Z]` on a channel config** refreshes each thin caller (`wf-ci.yml`, `wf-status.yml`, and `wf-client-page.yml` where installed) that is still exactly a released caller template, with the project's trusted branch and its own entry tag filled in, to the target release's caller template, and names that release as its entry. The target is `--rev` (a release tag v2.19.0 or later), else the release the project's channel is on now: its signed channel record, verified by the resolver (`adapters/resolve.mjs`, the trust root `bin/wf-resolve` and the gate use) with the project's `workflow.channel_key`, and this checkout's tag for it must be the record's commit. It is never this checkout's newest tag: a release that never passed the stable soak keeps its tag. When the record cannot be read or verified there is no default and it refuses, naming `--rev`. Whether a caller is unchanged is checked first: a caller the project changed is left untouched and listed under "Left as they are" as "a thin caller changed in this project", even when it already names the target; an unchanged caller ahead of the target is never moved back. A file with no entry line is not a thin caller yet: a released copy of the pre-channel workflow is replaced by the caller, anything else is listed as such. It writes no config (the channel and its keys stay), reports first, `--apply` writes and runs the target release's validator, and it never commits. Before, the plain form refused a channel config (no `workflow.revision`).
- **`--to-channel` defaults to the channel's release:** without `--entry`, the callers name the release the chosen channel is on now, from its signed record verified with the `--key`s given, not the pinned release's tag, so a project pinned at v2.19.0 opts in with the callers and entries its channel runs. Without a verified record it refuses; `--entry vX.Y.Z` still names the release.
- **A hold's thin callers move with its pin:** on a `workflow.revision` config, `bin/wf-upgrade` refreshes a file that is a thin caller with the caller logic above, to the target's release tag (also when the pin is already there), never with the copied-template logic; a target that is not a release tag v2.19.0 or later leaves it, listed.
- Tests (`validator/test/upgrade-channel-callers.test.js`): `bin/wf-upgrade` runs over fixture projects in a scratch workflow repository with two releases whose templates differ. A pinned project's plan moves the pin, refreshes an unchanged `wf-ci.yml` and lists a changed `wf-status.yml`; `--to-channel` from the older pin takes the newer entry and `--entry` the given one; a channel project's unchanged callers are rewritten to the newer templates and entry, the config stays, a second run has nothing to do and `--rev` with an older release moves nothing; a changed caller is listed and left byte for byte. The default is the channel's record, not a newer tag (a v2.19.2 tag stable has not reached), follows a promotion, refuses without a record and yields to `--rev` / `--entry`; a hold's callers move with the pin and at the same pin; a changed caller at the target is listed, not "already current"; a pre-channel copy is replaced, a changed one listed as not a thin caller yet.
- Upgrade: `bin/wf-upgrade --project PATH` from a workflow checkout with the new tags (`git pull --tags`), on every project. A pinned project moves its pin, and an unchanged copy of `.github/workflows/wf-ci.yml` takes the new `group:` line (a hold's unchanged thin callers move to the new pin's tag); a channel project's unchanged callers move to the callers and entry of the release its channel is on, so a stable project moves once v2.19.1 reaches stable. A changed copy or caller is listed by the plan for a merge by hand. Until a project's `wf-ci.yml` is refreshed the old race remains: rerun the cancelled `wf ci`. No step for a person goes into `upgrades.json`: what a project changed is listed by the plan itself, as for every release, so `validator/test/channel-compat.test.js` keeps its rule without an exception. The release commit sets the version and adds the `upgrades.json` entry.

## v2.19.0

2026-11-08. A minor release, the first of the central release channel (docs/proposals/2026-11-07-central-release-channel.md, as amended: a channel record signed by the release broker is the trust root). A project may name a channel instead of a pin; pinned projects keep working unchanged, and nothing is required to move the pin.

- **`bin/wf-resolve`** (part 1, contract *channel-resolve v3*): the base branch's config to the release that judges. A hold (`workflow.revision`) returns its pin; a channel (`workflow.channel`) resolves only through `channel-<name>.json` and its Ed25519 signature on the `channels` release, verified with `workflow.channel_key` from the base config, unexpired, valid for at most 72 hours, naming a revision on `main` that its tag points at and whose `package.json` carries its version; anything else fails closed. In CI `--base` is required, and in a pull request run it must be the event's `pull_request.base.sha`.
- **One shared gate** (part 2): `.github/workflows/wf-gate.yml` is a reusable workflow (`on: workflow_call`), the entry a project's thin caller names at an immutable release tag (`uses: Cazy00/agent-workflow/.github/workflows/wf-gate.yml@v2.19.0`, repeated as `with: entry: v2.19.0`). It runs `bin/wf-resolve` from that tag over the base commit's config (pull request: `pull_request.base.sha`; a trusted-branch run: its head), records `{channel, revision, version}` (with `seq` for a channel and `resolved_at`) as the check run `wf resolved` on the judged commit (the caller grants `checks: write`), then runs `bin/wf-gate-ci` from the resolved revision. A pin from before v2.19.0 has no `bin/wf-gate-ci` and is refused with the first opt-in step.
- **`bin/wf-gate-ci`**: the body of the copied `wf-ci.yml`'s *Run the gate* step, now versioned with the validator. In a pull request it first checks the head's `.github/workflows/wf-ci.yml` calls the entry exactly once, at a `vX.Y.Z` tag no older than `v2.19.0` and repeated as `entry` (it says which rule failed), then runs `wf ci` (enforced and owner-merge modes) or `wf records` (manual mode). A scheduled or dispatched run checks the trusted branch's records. `wf ci`'s JSON `workflow` carries `channel`, `revision`, `version` and `resolved_at`, and the summary says `Judged by agent-workflow v2.19.0 (abc123def456), channel stable, resolved at <time>.`
- **The shared status entry** `.github/workflows/wf-status.yml` (reusable): the same resolve and record steps word for word, `wf status` from the resolved revision, and the judged line with the `wf resolved` record in the *Project status* issue.
- **Thin callers** `templates/github/channel/wf-ci.yml` and `wf-status.yml`: triggers, permissions, concurrency and the entry only, with `workflow_dispatch`, `repository_dispatch` (type `wf-channel`, which the broker sends after a channel move) and a daily `schedule` on the trusted branch, which keep a canary project's soak fresh. Their check is reported as `wf ci / gate` (GitHub names a reusable workflow's job `<caller job> / <called job>`), so a project's required check and merge route move to that name when it opts in.
- **`workflow.channel` and `workflow.channel_key` in the config schema** (part 3): a channel is `stable`, `canary`, or `stable-N` / `canary-N` for a major N above 2; it needs `channel_key`, `ed25519:<base64 of a 32-byte key>` or a list of one to four different ones, and is refused beside a `workflow.revision`. A hold may carry `channel_key`. A milestone in progress names the channel as its `workflow_version`, as it names the pin today (`wf records`, and `wf ci` for a newly authorised one).
- **`bin/wf-upgrade --to-channel NAME --key ed25519:… [--key …] [--entry vX.Y.Z]`**, the second opt-in pull request: from a pin at v2.19.0 or later (an older pin is refused with the first step) or from another channel, it writes `workflow.channel` and `workflow.channel_key` in place of `workflow.revision` and `workflow.version`, moves the profile and each milestone in progress to the channel, and replaces `wf-ci.yml` and `wf-status.yml` with the thin callers at the entry tag (default: the pinned release's) where the project has not changed them, else lists them. It reports first, `--apply` writes, and the entry release's validator checks the records. It says what stays by hand: the required check's new name, the Actions policy, and a copied `scripts/wf` or `wf-client-page.yml` that the project changed (a copy that predates channels fails on a channel config; an unchanged one is replaced).
- **`approval.checkpoint: notice`** (part 4, opt-in; the default stays `milestone`): the agent merges every pull request once the gates pass. What owner-merge leaves to the owner (the milestone plan, the acceptance, governing and workflow paths, acceptance tests, accepted findings, the records the owner approves) is still detected and reported as `notice: <reason>` findings and in `notices`, on the check's summary and as a notice beside it; `wf ci` reports `merge: agent` with no owner reasons, and nothing is held between milestones. `notice` needs `acceptance_evidence: true` (refused without it, at the candidate too; `wf-adopt` sets it), so `wf ci` checks the acceptance record and demo of every acceptance the agent merges. Under every cadence and checkpoint, a move into Released from a status before Accepted needs the acceptance evidence too, as a move to Accepted does. Under `notice` a project's release pull request is the agent's merge, once its gates pass, and the owner is told. With `defer_to_acceptance`, what waits for the acceptance is also a `notice:` line on the pull request that defers it, and the acceptance's evidence lists it. A pull request runs its own copy of `.github/`, so no check run from it can be trusted for a change to that workflow: under `notice` such a change stays a `notice: enforcement path, host gate review required` line (`merge: agent`; `wf ci` does not claim to block it), and the protection is the host's merge gate, which must require an independent review for workflow and enforcement paths before an agent may merge (projects that use `notice` must run one; without one, keep `milestone`). Every other change, workflow config included, is judged by the base's copy. `notices` is returned on a failing verdict too. `wf next` follows it: under `notice` it tells the agent to merge a finished task's pull request, or a verified milestone's acceptance pull request, once the gates pass, never to wait for the owner's merge or acceptance, and says the held reasons are reported as `notice:` lines; under `milestone` it is unchanged. `defer_to_acceptance` and `auto_merge` accept it; `bin/wf-adopt --checkpoint notice` scaffolds it. Tests in `validator/test/checkpoints.test.js`: each held reason under `milestone` and `notice`, auto-merge under `notice`, an invalid value refused, the summary renderer, and `wf next` under both; a `.github/` change giving the `notice:` line and `merge: agent` (and no `--trusted-workflow` flag), notice without `acceptance_evidence` refused, an unevidenced acceptance and a move from Authorised to Released failing, and deferred items as notices.
- **`bin/wf-install`** (part 5, contract *channel-install v1*, `adapters/install.mjs`): the per-user installation sessions read instead of a copy per project. `--channel NAME --key …` resolves the channel with the resolver (nothing else chooses the revision), writes the verified commit once to `revisions/<hash>/` (read-only), then switches `channels/<name>` to it atomically (a new symlink renamed over the old) with the resolution in `channels/<name>.json`; a refused resolution changes nothing. `--revision HASH` installs a hold (a revision on `main`) with no pointer. `--use NAME|HASH` is a session's start: it prints the directory the session reads to its end and marks it used, so a later move never mixes two releases in one task. `--prune` removes a revision no pointer names and no session used in the last 7 days (`--days`). The root is `${XDG_DATA_HOME:-~/.local/share}/agent-workflow` unless `--root`. Tests: `validator/test/wf-install.test.js`.
- **`bin/wf-channel-audit --revision X --repo OWNER/NAME …`** (part 5, contract *channel-audit v1*, `adapters/audit.mjs`, read-only): after a bad release, the merged pull requests each project's gate judged at X (a full hash or a prefix of 7 or more), from the `wf resolved` check runs on their heads; only check runs made by GitHub Actions count. Before switching `WF_GATE` on, delete or update any branch carrying v2.5.0's `wf-ci.yml`, and turn on "Automatically delete head branches".

- **The containers come back after a power cut** (found on the owner's home server). `ci-runner create` sets `boot.autostart` on each container itself, not only on its profile, because LXD's snap starts its daemon at boot only when an instance itself has it. `install-host.sh` also starts LXD's daemon at every boot. Re-running `create` on an existing container repairs it.
- **The README covers sizing and LXD updates:** sizing per project (6 + 1 GiB each) and protecting remote access from the out-of-memory killer. LXD updates reload the daemon without stopping running containers; a refresh window or a hold is still offered.

## v2.1.0

Lets owner-approved acceptance tests be approved before the work and fail until it is done, in every mode (MAINT-0012). Before this, every mapped test had to pass on every production pull request, so tests written ahead of the work blocked every other task until all of them passed.

- **Pending scenarios,** in a project whose config names `paths.acceptance_tests` (so the owner approves its acceptance tests): while a milestone is `Authorised`, `Active` or `Blocked`, the mapped tests of a scenario it lists may fail as long as a task of that milestone serving the scenario is neither `Done` nor delivered by the candidate.
