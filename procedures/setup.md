# Establish a project

Default timebox: two working days. Use `templates/setup.md`; record actual time and usage, or unknown. Start in assisted mode. If the timebox is insufficient, the owner explicitly narrows supported scope or extends it. Do not label incomplete controls operational.

1. Create the profile and brief. Define source precedence, users, outcomes, scope, exclusions, journeys/data, risks, decisions, verification and delivery. Record unknowns with a required-before stage. Preserve distinctions between approved requirements, prototypes, historical records and derived indexes.
2. Verify the personal GitHub owner username; create/retain the repository there. Verify the development worker username independently. Configure separate human and agent clones and follow `identity.md`. Do not switch global accounts. Worktrees isolate concurrent work only.
3. Adopt an immutable workflow tag and commit. Copy the templates and shared procedures; point `AGENTS.md` and `CLAUDE.md` to them. Record the tag and hash in project config. Keep active milestones on their adopted version until explicitly upgraded.
4. Classify all paths by effects, including migrations, scripts, dependency/configuration files, infrastructure and generated inputs/outputs. Mark all approval records and enforcement surfaces protected. Unclassified paths block integration. External skills/tools require inspection of instructions/scripts/permissions/dependencies, a pinned version, representative testing and a toolbox record before adoption.
5. Establish owner-controlled bootstrap, then record when normal protections become active. Protect approved requirements, acceptance definitions, decisions, workflow configuration, validators, runners, CI, and CODEOWNERS. Require owner review, stale-review invalidation, administrators subject to restrictions, no worker bypass, and trusted checks bound to their producing application. Verify check provenance and the protected CI entry point, not only its name. Check GitHub plan support and record unavailable controls.
6. Provision the trusted validator and owner public key outside the agent clone. The current implementation supports **explicit manual signed approval receipts** (`approval-evidence.md`). It does not infer approval from GitHub branch contents. Install the launcher outside candidate control for authoritative runs; bind its full revision in protected runner configuration. Local copied launchers only provide feedback. Use a protected external checker or owner-controlled manual run, with its result tied to the exact candidate. Candidate tests run separately without owner credentials or signing keys.
7. Define acceptance IDs and methods in `docs/workflow/acceptance.json`, mappings in `tests/acceptance-map.json`, and required checks in the profile. Capture actual reporter output, environment, revision, and limitations. The owner-controlled collector verifies provenance and signs receipts after examining raw evidence. No candidate `passed` field supplies evidence by itself.
8. Run the gate, acceptance, identity and session fixtures. Test tool instruction discovery in a fresh Codex session and a fresh Claude Code session: ask each to identify governing policy, ready work, pending authority, and its permitted next action; then give a blocked task and confirm no production edit. Record actual tool version, prompt, transcript and result. Reading the adapter files alone is not a discovery test.
9. Run a real approval-path test in an authorised disposable branch/repository: worker direct push and unapproved protected change must be rejected; owner approval plus authentic checks permits the intended change; stale approval becomes invalid. Do not probe a production branch destructively. Record requested action, observed rejection/acceptance and resulting revision.
10. For central feedback, provision the external operations config and private runtime directory using `operations.md`. Record the owner-authorised public data boundary and issue worker. Test actual instruction discovery and reporter calls from both Codex and Claude Code, plus wrong/missing identity and unknown delivery. Do not claim least privilege from one successful issue write.
11. Pilot a small authorised milestone under observation. Record technical and workflow outcomes separately using `templates/pilot.md`. Verify review, integration and acceptance before considering unattended execution.

The runner is **not adopted** in this implementation. Unattended mode requires a separately approved runner, duplicate-claim prevention, persistent cumulative budgets, bounded calls/retries, child-process cleanup, interrupted-action recovery, and all runner fixtures plus a pilot. Graphify and other generated navigation tools remain deferred optional tools, not missing prerequisites.
