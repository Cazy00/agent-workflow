# Establish a project

Read for setup: this file, `identity.md`, `templates/profile.md`, `templates/setup.md` and `config.default.json`. Consult `POLICY.md`, `SCHEMA.md` and the other procedures only when a rule is unclear or a step points to them; do not load them up front.

Default timebox: two working days. Use `templates/setup.md`; record actual time and usage per step, or unknown. Start in assisted mode. If the timebox is insufficient, the owner explicitly narrows supported scope or extends it. Do not label incomplete controls operational.

## Who does what

Each step is tagged **script**, **agent** or **owner**. The agent performs the script step and the agent steps, writes the owner steps into the setup record as a checklist stating what each needs, posts that, and stops. It never attempts, retries or waits on an owner step, and never asks for credentials, keys or protection changes to be handed to it. Owner steps need the owner's accounts and cannot be delegated. `bin/wf-adopt` performs the script step and writes the checklist for the arrangement chosen below; `bin/wf-protect` and `bin/wf-sign` turn the owner's GitHub and key steps into one command each.

## Choose the arrangement

Two owner choices decide which owner steps apply. Pass them to `bin/wf-adopt`; the profile's *Authority* records them.

- **Accounts.** With a worker account (`--worker NAME`) the agent publishes under its own GitHub identity (step 2), and enforced mode is possible. With one account, the default, the agent works with the owner's account: step 2 and separate clones fall away, nothing on GitHub tells the agent's actions from the owner's, and enforced mode is unavailable, because GitHub never lets an author approve their own pull request. One account is an approved deviation from POLICY § 7.
- **Approval** (`--approval`). `manual`, the default: the owner signs receipts with a key `bin/wf-sign` makes; it works on any plan and with one account. `owner-merge`, for one owner: the owner's own review and merge of each pull request is the approval; nothing to provision, but nothing proves who merged, so the setup record says so and routine delegation is unavailable (`approval-evidence.md`). `enforced`: the protections carry approval; it needs rulesets, a worker account and step 9, so it is reached by a reviewed switch and never scaffolded.

Rulesets need a public repository or a GitHub Pro or Team plan for a private one. Without them every mode but enforced still works; step 5 is skipped and recorded.

## Stop rule for the agent

The agent's setup work is its steps only, one session at a time, and half a working day of its own wall-clock time in total unless the owner records another allowance in the setup record. At the end of each session it records in the setup record what each step consumed (time and usage, or unknown), the owner checklist and the next agent step, posts that, and stops; the next session continues from the record. Setup in one long session with no stop is what exhausts an allowance.

The runner is **not adopted** in this implementation. Unattended mode requires a separately approved runner, duplicate-claim prevention, persistent cumulative budgets, bounded calls/retries, child-process cleanup, interrupted-action recovery, a pause proven by observed silence rather than by a stop instruction, and all runner fixtures plus a pilot. Graphify and other generated navigation tools remain deferred optional tools, not missing prerequisites.

## Two starting points, one set of controls

**New project:** the script step, the agent steps, then the owner checklist. The first milestone is the observed pilot (step 11).

**Existing repository:** the same controls in the same order, with three rules that keep the cost bounded. Do not inventory the codebase: fill the profile's *Starting position* and *Technical context* from what the owner says and from the README, manifests and directory listing, and leave the rest under *Unknowns* with the stage at which each becomes required; the codebase is learned per task. Classification is a config edit, not a survey: `wf ci` classifies only the paths a candidate changes, and `config.default.json` already covers common source; add the stack's missing patterns (for example `**/*.{dart,vue,svelte}`, `Cargo.toml`, `requirements.txt`) and stop. Keep the first milestone small enough to serve as the pilot. Porting the code into a fresh repository under the owner account is an option the owner may choose when the old repository's protections, collaborators or CI are hard to verify; it simplifies the owner steps and none of the agent steps, and it loses GitHub-side history and integrations. Record the choice in the setup record.

## Steps

1. **[agent]** Create the profile and brief from the owner's input, including anything in `docs/workflow/inbox/`. Define source precedence, users, outcomes, scope, exclusions, journeys/data, risks, decisions, verification and delivery. Record unknowns with a required-before stage. Preserve distinctions between approved requirements, prototypes, historical records and derived indexes.
2. **[owner, with a worker account]** Verify the personal GitHub owner username; create/retain the repository there. Verify the development worker username independently and give it write access. Configure separate human and agent clones and follow `identity.md`. Do not switch global accounts. Worktrees isolate concurrent work only. A shared project adds the steps in `shared.md`. With one account, skip this step; the profile's *Authority* records the arrangement.
3. **[script]** Adopt an immutable workflow tag and commit: `bin/wf-adopt` writes `docs/workflow/config.json` with the tag, full hash and approval identities, the record directories, the profile, setup and acceptance seeds, the local launcher, the `AGENTS.md` / `CLAUDE.md` adapters, `.github/CODEOWNERS`, `.github/workflows/wf-ci.yml` (the `wf ci` check: the validator pinned by the pull request's base branch, fetched fresh, judging its head; records only in manual mode; protected only where code-owner review covers it) and `.github/workflows/wf-status.yml` when absent, and fetches the pinned installation. Commit the scaffold to the trusted branch before anything else; `wf next` says so until it is. That workflow republishes `wf status` with the open pull requests to a *Project status* issue after each push to the trusted branch, and every six hours when that is the default branch. It is a convenience view that approves nothing and that a collaborator's own workflow could also edit, so check consequential items against the records and pull requests; it is public on a public repository. A trusted branch other than `main` is set in both `docs/workflow/config.json` and that file; delete the file to opt out. Keep active milestones on their adopted version until explicitly upgraded.
4. **[agent]** Classify by effect what the defaults miss for this stack: migrations, scripts, dependency/configuration files, infrastructure and generated inputs/outputs. Approval records and enforcement surfaces are protected by the defaults; keep them so. Unclassified changed paths block integration. External skills/tools require inspection of instructions/scripts/permissions/dependencies, a pinned version, representative testing and a toolbox record before adoption.
5. **[owner, optional]** Establish owner-controlled bootstrap, then the protections, where rulesets are available; otherwise record that they are not. With the scaffold on the trusted branch, the owner runs `bin/wf-protect --project . --apply` from the installation with their own `gh` login. It creates or updates one ruleset, `agent-workflow`, on the trusted branch, shaped by the approval mode, and reads it back; without `--apply` it only reads. In every mode the branch cannot be deleted or force-pushed and nobody, administrators included, can bypass. **Manual** stops there, since the owner's closeout fast-forward must still push, and turns auto-merge off. **Owner-merge** adds a pull request, the `wf ci` check and every entry of the profile's `required_checks` from GitHub Actions on an up-to-date branch, and stale reviews dismissed, with no required review (one account can never approve its own pull request) and auto-merge off, which would let the agent's pull requests merge on their checks alone. **Enforced** (`--target enforced`) adds code-owner review with **0** required approvals and approval of the most recent push **off**, so a records-only pull request merges after its checks while any other waits for the owner, and auto-merge on, which the agent turns on for each pull request it opens; classic branch protection cannot require 0 approvals. `CODEOWNERS`, written by the scaffold, is `* @OWNER` then the unowned lines `/docs/workflow/tasks/` and `/docs/workflow/feedback/` (after `*`, since the last matching line wins); GitHub enforces it only under code-owner review. Rerun `--apply` when approving a profile change to `required_checks`, so the integration rerun (POLICY § 9, layer 3) runs on the assembled candidate and a failing check blocks the merge. Record the single-owner settings in the profile's *Authority* as an approved deviation (IDEA-18). A shared project keeps every path owned and requires approval of the most recent push (`shared.md`). Optionally pin the *Project status* issue once the status workflow has opened it.
6. **[owner]** Provision what the approval mode needs (`approval-evidence.md`). **Owner-merge**: nothing; `wf-ci.yml` runs the `wf ci` check, the owner merges only what they have reviewed, and the agent never merges. Nothing protects that workflow in this mode: a pull request runs its own copy, and could add another job named `wf ci`, so the owner checks every change under `.github/` before merging. **Enforced**, where rulesets and a worker account are available: once step 9 passes, set `approval.label` in `docs/workflow/config.json` and `approval_label` in the profile to `enforced` in one code-owner-reviewed pull request; the fetched authoritative branch is then the approved baseline, no signing key is needed, and the checker lists receipt-dependent evidence as `unverified` for the pull request review. **Manual signed receipts**, the scaffold's default: `bin/wf-sign --keygen DIR`, outside every checkout, writes a passphrase-protected key and its public key (the passphrase keeps the key from an agent running as the owner), and the owner signs each round with `bin/wf-sign`; name the signing drop in `$WF_SIGNING_DIR` beside `$WF_RECEIPTS`, outside every checkout; decide whether to enable derived baselines (`approval.derived_baselines`), which spare the baseline receipt for a Done record after a signed candidate and for a close whose change receipt lists what it changes (`approval-evidence.md`, *Derived baselines*); and add an `attest` section with the stack's setup and check commands, plus a sandbox launcher outside every checkout, so the verification the owner signs comes from the owner's own run (*Attested evidence*). In manual and enforced modes install the launcher outside candidate control for authoritative runs and bind its full revision in protected runner configuration; local copied launchers only provide feedback; the required check must run the pinned validator from the protected CI entry point, with its result tied to the exact candidate; candidate tests run separately without owner credentials or signing keys.
7. **[agent]** Define the profile's `required_checks`: the stack's applicable type, build, lint, component-boundary and test commands, named as CI reports them, or the recorded reason one does not apply; readiness fails while the list is empty. Define acceptance IDs and methods in `docs/workflow/acceptance.json` and mappings in `tests/acceptance-map.json` for the first milestone only, with the mapped tests under `paths.acceptance_tests` (`tests/acceptance/` by default) so that changing them needs the owner's receipt. IDs look like `AC-001-1` (milestone number, then example number), as in `templates/acceptance.json`; `wf records` checks both files. Capture actual reporter output, environment, revision, and limitations. In manual mode the owner-controlled collector verifies provenance and signs receipts after examining raw evidence; in enforced mode the evidence is posted on the pull request for the code-owner review. No candidate `passed` field supplies evidence by itself.
8. **[agent, own session]** Run the gate, acceptance, identity and session fixtures. Test tool instruction discovery in a fresh Codex session and a fresh Claude Code session: ask each to identify governing policy, ready work, pending authority, and its permitted next action; then give a blocked task and confirm no production edit. Record actual tool version, prompt, transcript and result. Reading the adapter files alone is not a discovery test. Do this in its own session, not the one that wrote the profile.
9. **[owner, only to switch to enforced]** Verify the protections: `bin/wf-protect --project . --target enforced` must pass. It reads back the ruleset, its bypass list, each required check and the application bound to it, auto-merge, `CODEOWNERS` and the two accounts. Settings read back are the default evidence; they show configuration, not behaviour. The live approval-path test is optional, stronger evidence, and required in a shared project to show that a worker's approval cannot merge: in an authorised disposable branch or repository, a worker direct push and an unapproved protected change are rejected, a records-only pull request merges after its checks while one touching an owned path waits, owner approval plus authentic checks admits the change, a stale approval becomes invalid, and bringing an approved branch up to date shows which checks rerun and whether approval is dismissed. Never probe a production branch destructively. Record the evidence; then complete the switch from step 6. A single-owner project also replaces its `AGENTS.md` sentence that forbids auto-merge, in the same pull request, with: "When the repository allows auto-merge, turn it on as you open the pull request (`gh pr merge --auto` with the merge method the repository allows); bring a branch that falls behind up to date (`gh pr update-branch`); after a settings change, rerun a check so auto-merge re-evaluates. Never approve, merge by hand, sign or bypass a rule yourself", keeping what follows it.
10. **[owner, then agent; optional, off by default]** For central feedback, provision the external operations config and private runtime directory using `operations.md`. Record the owner-authorised public data boundary and issue worker. Then test actual instruction discovery and reporter calls from both Codex and Claude Code, plus wrong/missing identity and unknown delivery. Do not claim least privilege from one successful issue write.
11. **[owner and agent]** The first milestone is the pilot: keep it small and watch it. Record technical and workflow outcomes separately using `templates/pilot.md`. Verify review, integration and acceptance before considering unattended execution.

## Shared project

When two or more people share the owner role, `shared.md` adds its setup steps.

## Reuse an existing setup

Start with `bin/wf-adopt --inspect --project /path/to/project`. Its bounded read-only inventory identifies existing manifests, CI hints, adoption and collisions without executing the project. Reuse adequate profile/design/identity/check/protection evidence after verifying its revision, configuration and applicability; do not reinstall or repeat an unchanged successful setup step. Record only gaps and changed controls. Inspection does not verify access, protections or check execution. Confirm actual CI job names and run the required checks before claiming readiness.

For fewer owner interactions, prepare one concrete checklist for the account/protection actions that genuinely require the owner, complete all worker-accessible work first, and verify each control once. Keep planning unknowns from blocking unrelated setup. Existing authenticated operational routes should be checked before requesting credentials or moving backups manually; never print secrets or shift technical verification to the owner. Optional batching and agent-operated routine integration use `delivery.md`, with their own adverse approval-path tests before activation.
