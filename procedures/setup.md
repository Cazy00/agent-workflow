# Establish a project

Read for setup: this file, `identity.md`, `templates/profile.md`, `templates/setup.md` and `config.default.json`. Consult `POLICY.md`, `SCHEMA.md` and the other procedures only when a rule is unclear or a step points to them; do not load them up front.

Default timebox: two working days. Use `templates/setup.md`; record actual time and usage per step, or unknown. Start in assisted mode. If the timebox is insufficient, the owner explicitly narrows supported scope or extends it. Do not label incomplete controls operational.

## Who does what

Each step is tagged **script**, **agent** or **owner**. The agent performs the script step and the agent steps, writes the owner steps into the setup record as a checklist stating what each needs, posts that, and stops. It never attempts, retries or waits on an owner step, and never asks for credentials, keys or protection changes to be handed to it. Owner steps need the owner's accounts and cannot be delegated. `bin/wf-adopt` performs the script step and writes the checklist for the arrangement chosen below; `bin/wf-protect` and `bin/wf-sign` turn the owner's GitHub and key steps into one command each, and `bin/wf-setup` offers the scaffold's choices, the settings and the owner's checklist as a local page.

## Choose the arrangement

Three owner choices decide which owner steps apply. Pass them to `bin/wf-adopt`, or answer them on `bin/wf-setup`'s page; the profile's *Authority* records them.

- **When the agent stops** (`--checkpoint`, with owner-merge approval). `milestone`, the default: the agent merges each task's pull request once the gates pass and stops when a milestone is finished, until the owner has tried and accepted it. `change`: the owner merges every pull request. `plan`: as `milestone`, without stopping between the milestones the owner has authorised. The same gates run in each, and governing, workflow and acceptance-test changes always wait for the owner (`approval-evidence.md`, *Owner-merge mode*).
- **Accounts.** With a worker account (`--worker NAME`) the agent publishes under its own GitHub identity (step 2), and enforced mode is possible. With one account, the default, the agent works with the owner's account: step 2 and separate clones fall away, nothing on GitHub tells the agent's actions from the owner's, and enforced mode is unavailable, because GitHub never lets an author approve their own pull request. One account is an approved deviation from POLICY § 7.
- **Approval** (`--approval`). `owner-merge`, the default for one owner: the owner's merge is the approval, under the checkpoint above; nothing to provision, but nothing proves who merged, so the setup record says so. `manual`, the default for a shared project and the choice for proof: the owner signs receipts with a key `bin/wf-sign` makes and so approves every change; it works on any plan and with one account. `enforced`: the protections carry approval; it needs rulesets, a worker account and step 9, so it is reached by a reviewed switch and never scaffolded.

Rulesets need a public repository or a GitHub Pro or Team plan for a private one. Without them every mode but enforced still works; step 5 is skipped and recorded.

## Stop rule for the agent

The agent's setup work is its steps only, in two sessions: steps 1, 4 and 7, which edit the profile, the config and the acceptance files, then step 8 in a fresh context. Its allowance is half a working day of its own wall-clock time in total unless the owner records another in the setup record. At the end of each session it records in the setup record what each step consumed (time and usage, or unknown) and the next agent step, posts that, and stops; the next session continues from the record. What exhausts an allowance is studying the codebase or the workflow, not the number of steps: read only the setup reading list and what the owner gives.

The runner is **not adopted**: unattended mode needs what POLICY § 8 *Runner requirements* lists, its fixtures and a pilot. Graphify and other generated navigation tools remain deferred optional tools, not missing prerequisites.

## Two starting points, one set of controls

**New project:** the script step, the agent steps, then the owner checklist. The first milestone is the observed pilot (step 11).

**Existing repository:** the same controls in the same order, with three rules that keep the cost bounded. Do not inventory the codebase: fill the profile's *Starting position* and *Technical context* from what the owner says and from the README, manifests and directory listing, and leave the rest under *Unknowns* with the stage at which each becomes required; the codebase is learned per task. Classification is a config edit, not a survey: `wf ci` classifies only the paths a candidate changes, and `config.default.json` already covers common source; add the stack's missing patterns (for example `**/*.{dart,vue,svelte}`, `Cargo.toml`, `requirements.txt`) and stop. Keep the first milestone small enough to serve as the pilot. Porting the code into a fresh repository under the owner account is an option the owner may choose when the old repository's protections, collaborators or CI are hard to verify; it simplifies the owner steps and none of the agent steps, and it loses GitHub-side history and integrations. Record the choice in the setup record.

## Steps

1. **[agent]** Create the profile and brief from the owner's input, including anything in `docs/workflow/inbox/`. Define source precedence, users, outcomes, scope, exclusions, journeys/data, risks, decisions, verification and delivery. Record unknowns with a required-before stage. Preserve distinctions between approved requirements, prototypes, historical records and derived indexes.
2. **[owner, with a worker account]** Verify the personal GitHub owner username; create/retain the repository there. Verify the development worker username independently and give it write access. Configure separate human and agent clones and follow `identity.md`. Do not switch global accounts. Worktrees isolate concurrent work only. A shared project adds the steps in `shared.md`. With one account, skip this step; the profile's *Authority* records the arrangement.
3. **[script]** Adopt an immutable workflow tag and commit: `bin/wf-adopt` writes `docs/workflow/config.json` with the tag, full hash and approval identities, the record directories, the profile, setup and acceptance seeds, the local launcher, the `AGENTS.md` / `CLAUDE.md` adapters, `.github/CODEOWNERS`, `.github/workflows/wf-ci.yml` (the `wf ci` check: the validator pinned by the pull request's base branch, fetched fresh, judging its head with the delivery evidence from its description; records only in manual mode; protected only where code-owner review covers it) and `.github/workflows/wf-status.yml` when absent, and fetches the pinned installation. Commit the scaffold to the trusted branch before anything else; `wf next` says so until it is. That workflow republishes `wf status` with the open pull requests to a *Project status* issue after each push to the trusted branch, and every six hours when that is the default branch. It is a convenience view that approves nothing and that a collaborator's own workflow could also edit, so check consequential items against the records and pull requests; it is public on a public repository. A trusted branch other than `main` is set in both `docs/workflow/config.json` and that file; delete the file to opt out. Keep active milestones on their adopted version until explicitly upgraded.
4. **[agent]** Classify by effect what the defaults miss for this stack: migrations, scripts, dependency/configuration files, infrastructure and generated inputs/outputs. Approval records and enforcement surfaces are protected by the defaults; keep them so. Unclassified changed paths block integration. External skills/tools require inspection of instructions/scripts/permissions/dependencies, a pinned version, representative testing and a toolbox record before adoption.
5. **[owner, optional]** Establish owner-controlled bootstrap, then the protections, where rulesets are available; otherwise record that they are not. With the scaffold on the trusted branch, the owner runs `bin/wf-protect --project . --apply` from the installation with their own `gh` login. It creates or updates one ruleset, `agent-workflow`, on the trusted branch, shaped by the approval mode, and reads it back; without `--apply` it only reads. In every mode the branch cannot be deleted or force-pushed and nobody, administrators included, can bypass. **Manual** stops there, since the owner's closeout fast-forward must still push. **Owner-merge** adds a pull request, the `wf ci` check and every `required_checks` entry from GitHub Actions on an up-to-date branch, with no required review (one account can never approve its own pull request). **Enforced** (`--target enforced`) adds code-owner review with **0** required approvals, so a records-only pull request merges after its checks while any other waits for the owner, and auto-merge on; auto-merge is off in the other modes. `CODEOWNERS`, written by the scaffold, is `* @OWNER` then the unowned `/docs/workflow/tasks/` and `/docs/workflow/feedback/`; GitHub enforces it only under code-owner review. Rerun `--apply` when approving a change to `required_checks`, so a failing check blocks the merge. Record the single-owner settings in the profile's *Authority* as an approved deviation. A shared project keeps every path owned and requires approval of the most recent push (`shared.md`).
6. **[owner]** Provision what the approval mode needs (`approval-evidence.md`). **Owner-merge**: nothing; `wf-ci.yml` runs the `wf ci` check, which needs the agent's delivery evidence and reports who merges each pull request under the checkpoint. Nothing protects that workflow in this mode: a pull request runs its own copy, and could add another job named `wf ci`, so the owner checks every change under `.github/` before merging. **Enforced**, where rulesets and a worker account are available: once step 9 passes, set `approval.label` in `docs/workflow/config.json` and `approval_label` in the profile to `enforced` in one code-owner-reviewed pull request; the fetched authoritative branch is then the approved baseline, no signing key is needed, and the checker lists receipt-dependent evidence as `unverified` for the pull request review. **Manual signed receipts**: `bin/wf-sign --keygen DIR`, outside every checkout, writes a passphrase-protected key and its public key (the passphrase keeps the key from an agent running as the owner), and the owner signs each round with `bin/wf-sign`; the signing drop, derived baselines and attested evidence are set up as `approval-evidence.md` describes. In manual and enforced modes install the launcher outside candidate control for authoritative runs and bind its full revision in protected runner configuration; local copied launchers only provide feedback; the required check must run the pinned validator from the protected CI entry point, with its result tied to the exact candidate; candidate tests run separately without owner credentials or signing keys.
7. **[agent]** Define the profile's `required_checks`: the stack's applicable type, build, lint, component-boundary and test commands, named as CI reports them, or the recorded reason one does not apply; readiness fails while the list is empty. Define acceptance IDs and methods in `docs/workflow/acceptance.json` and mappings in `tests/acceptance-map.json` for the first milestone only, with the mapped tests under `paths.acceptance_tests` (`tests/acceptance/` by default) so that changing them needs the owner's receipt. IDs look like `AC-001-1` (milestone number, then example number), as in `templates/acceptance.json`; `wf records` checks both files. Capture actual reporter output, environment, revision, and limitations. In manual mode the owner-controlled collector verifies provenance and signs receipts after examining raw evidence; in enforced mode the evidence is posted on the pull request for the code-owner review. No candidate `passed` field supplies evidence by itself.
8. **[agent, fresh context]** Run `scripts/wf records` and `scripts/wf next` on the committed setup; the adopted release's own tests already ran the gate, acceptance, identity and session fixtures. For each agent tool the owner uses (Claude Code, Codex), test instruction discovery in a fresh context of that tool, a subagent or a new session, never the one that wrote the profile: ask it to identify governing policy, ready work, pending authority and its permitted next action; then give it a blocked task and confirm no production edit. Record the tool version, prompt and result. Reading the adapter files alone is not a discovery test.
9. **[owner, only to switch to enforced]** Verify the protections: `bin/wf-protect --project . --target enforced` must pass. It reads back the ruleset, its bypass list, each required check and the application bound to it, auto-merge, `CODEOWNERS` and the two accounts. Settings read back are the default evidence; they show configuration, not behaviour. The live approval-path test is optional, stronger evidence, and required in a shared project to show that a worker's approval cannot merge: in an authorised disposable branch or repository, a worker direct push and an unapproved protected change are rejected, a records-only pull request merges after its checks while one touching an owned path waits, owner approval plus authentic checks admits the change, a stale approval becomes invalid, and bringing an approved branch up to date shows which checks rerun and whether approval is dismissed. Never probe a production branch destructively. Record the evidence; then complete the switch from step 6, with the `AGENTS.md` sentence on auto-merge that `approval-evidence.md` *Enforced mode* gives, in the same pull request.
10. **[owner, then agent; optional, off by default]** Central feedback follows `operations.md`, with its own discovery and reporter tests.
11. **[owner and agent]** The first milestone is the pilot: keep it small and watch it. Record technical and workflow outcomes separately using `templates/pilot.md`. Verify review, integration and acceptance before considering unattended execution.

## Shared project

When two or more people share the owner role, `shared.md` adds its setup steps.

## Reuse an existing setup

Start with `bin/wf-adopt --inspect --project /path/to/project`. Its bounded read-only inventory identifies existing manifests, CI hints, adoption and collisions without executing the project. Reuse adequate profile/design/identity/check/protection evidence after verifying its revision, configuration and applicability; do not reinstall or repeat an unchanged successful setup step. Record only gaps and changed controls. Inspection does not verify access, protections or check execution. Confirm actual CI job names and run the required checks before claiming readiness.

Keep planning unknowns from blocking unrelated setup. Check existing authenticated operational routes before requesting credentials or moving backups manually; never print secrets or shift technical verification to the owner. Batching and routine integration use `delivery.md`, with their own adverse approval-path tests before activation.
