# Deploy, operate, maintain and upgrade

The flow does not end at release. Deployment, operation, maintenance and upgrades use the same records, the same four verification layers and the same authority rules; only the entry points differ. Record the project's actual arrangement in the profile's *Operations* and *Authority* sections. The defaults below apply where the profile is silent.

## Deployment

Name the environments (local, test, staging, production), who deploys to each and how. Default authority: the agent may deploy to the non-production environments the profile names; a production deployment is an owner action or an automatic pipeline from the trusted branch. When production deploys automatically from that branch, the owner's approval of the release pull request is the release authority, so `templates/release.md` must be satisfied before that merge, not after it. Deployment credentials stay outside the agent's reach (POLICY § 9). After every production deployment run the post-release verification the release record names and post the result on the pull request; a failed verification is an incident.

Before involving the owner in an operational rehearsal, inspect the existing authorised route and prepare the target, commands and test data. Reuse agent-accessible backup retrieval, configuration and dedicated test accounts; ask only for genuinely owner-only access or decisions, grouped into one concrete checklist. Record whether the owner must remain present. Do not repeatedly try an invisible UI/terminal or ask for the same credentials when the cause has not changed. If the owner explicitly chooses manual steps, respect that choice and keep instructions short. Secret values stay out of transcripts and evidence. Measure operational prompts separately from approvals so work is not merely shifted to the owner.

## CI runners

A project whose switches `CI_BUILD` and `WF_GATE` are `on` uses the owner's runners (`server/ci-runner/README.md`, private repositories only) and depends on them. When one is down, jobs queue and merges stall: cancel the waiting run, switch it off, then push again or edit the pull request's description; a runner offline for 14 days must be registered again. The runners are persistent. Any account that can push runs code on the build runner. The gate runs `wf ci` only for pull requests into the trusted branch, its jobs checking the branch name exactly, with the validator that branch pins, so code reaches it from an account that can change workflow files or the trusted branch. In owner-merge and manual modes, only the rules stop any account with write access from merging. Until each job gets a fresh container (MAINT-0017 D1), `wf ci` there is only as trustworthy as every account with write access. The labels are fixed in the workflow files and the variables only switch them, since any write collaborator can set a variable. Agents' credentials carry no workflow or runner rights (`server/ci-runner/README.md`), and a job holding deployment secrets stays on GitHub's runner. Record when `WF_READ_TOKEN` expires: from that day every project's `wf ci` fails to fetch the workflow.

## Incidents and the hotfix lane

An incident is production behaviour that breaks an accepted scenario, loses or exposes data, or stops the service. The coordinator records it as a decision of type `fact` (symptom, affected scenarios, time, evidence), opens a task under the affected milestone or the maintenance milestone, and pauses feature work that touches the affected area. Under an explicit owner instruction the four layers keep their content and relax only their order: capture evidence or reproduce; make the smallest fix with a regression check; verify; deploy through the authorised route; then obtain the independent review within the window the owner set (default: before the end of the next working day) and repeat any check the review invalidates. Rollback is reserved to the owner unless the profile delegates it and the release record shows it was exercised once. Every incident ends with its lesson recorded as a check or an acceptance example, or with a note saying why neither is possible.

## Routine maintenance

Dependency, security and platform updates, certificate and key rotation, backup verification and monitoring review form a standing **maintenance milestone** with its own limits, authorised once and renewed by the owner at each acceptance; each cycle is a task with the normal readiness, checks and review. A backup is verified by restoring it. Findings from monitoring, support requests and user feedback enter discovery as issues on the project repository or items in `docs/workflow/inbox/`; a finding becomes a task under an authorised milestone, or a decision when it changes scope, business behaviour or spending.

## Updates and upgrades

Product changes are new milestones. A project's move to a newer workflow version is a task of its own under an authorised milestone. Run `bin/wf-upgrade --project PATH` from an up-to-date workflow checkout (`git pull --tags`): it reports, and with `--apply` does, the move. It moves the pin, removes the config keys and files the releases in between no longer need (`upgrades.json`), refreshes the workflow files the scaffold installed where the project has not changed them, lists the files the project changed for you to merge by hand and the steps each release leaves to you, and runs the new release's `wf records`. It never commits; migrate any records the new schema needs, check that CI fetches the full history (`fetch-depth: 0`) that `wf ci` reads, and post the outcome on the upgrade's pull request. Move the pin once per upgrade, to the newest release that fixes what the upgrade found: a workflow defect found mid-upgrade is fixed and released before the pin moves, not after. A change to the pin alone (config `workflow`, profile `workflow_version`), with the config keys `wf-upgrade` removes, leaves every task's readiness fresh; any other change to either file does not. Both acceptance files are read from the baseline, so a project without them merges `docs/workflow/acceptance.json` and the config that classifies the new paths before the change that adds `tests/acceptance-map.json`. Active milestones stay on their adopted version unless the owner decides otherwise (`maintenance.md`): `wf-upgrade` moves each milestone in progress to the new version with the pin (`workflow_version`), and `wf records` refuses the two apart, so the owner's merge of the upgrade is that decision, and seen. A change to that line alone leaves its tasks' readiness fresh.

## Channels

A project may follow a release channel instead of a pin (v2.19.0). The host's release broker tags each release and moves the channels: `canary` is the newest release, `stable` follows after a 24 h soak. A channel record signed by the broker is the only thing a channel resolves through, so a project names the channel and the broker's public key (`workflow.channel`, `workflow.channel_key`), never a revision.

- **Moving to a channel** is a task of its own, two pull requests on the project's normal merge route: first move the pin to v2.19.0 or later (`bin/wf-upgrade --project PATH`), then run `bin/wf-upgrade --project PATH --to-channel stable --key ed25519:… --apply` (`canary` for a project that soaks releases). The thin callers it writes name, as their entry, the release the chosen channel is on now: read from its signed channel record and verified with the keys you pass, as `bin/wf-resolve` verifies it, never this checkout's newest tag (a release still soaking on canary keeps its tag). When that cannot be read and verified (offline, an expired or unsigned record, this checkout's tag not the record's commit) it refuses; `--entry vX.Y.Z` names the release yourself. It reports first and never commits; it lists what stays by hand, among them the required check's new name (`wf ci / gate`). A pin from before v2.19.0 is refused with the first step.
- **Moving a channel project's callers.** The channel moves the shared gate, not the project's thin callers, which name their entry tag; a change to the callers or the entries reaches a project only when its callers name the newer tag. `bin/wf-upgrade --project PATH` on a channel config refreshes each caller that is still a released caller template to the caller of the release the project's channel is on now (from its signed channel record, as `bin/wf-resolve` verifies it; without a verified record it refuses, and `--rev vX.Y.Z` names the release yourself), entry tag included. A caller is never moved back; one the project changed is listed as a step by hand, and an unchanged copied workflow from before channels is replaced by its caller. It writes no config and never commits; open a pull request for the result as for any upgrade. Run it after each release; with nothing to move it says so.
- **A hold** is a project that stays on one revision: `workflow.revision` (a full hash on `main`) and no `workflow.channel`; the two are refused together. A hold keeps working unchanged and nothing moves it but its own upgrade: `bin/wf-upgrade --project PATH` moves the pin and, where the hold still has thin callers, moves them to the new pin's release tag too (a target that is not a release tag v2.19.0 or later leaves them, listed). To leave a channel for a hold, or the reverse, change the config in a pull request of its own under an authorised milestone.
- **Which revision a project runs.** `scripts/wf next` names the channel and the revision it is at (`Workflow: … channel stable, now vX.Y.Z (<revision>)`), and every judged pull request carries the check run `wf resolved` with `{channel, revision, version}`. A session reads one revision to its end: `wf-install --use NAME` prints the directory and keeps it for the task, so a channel move never mixes two releases in one task. After a bad release, `bin/wf-channel-audit --revision X --repo OWNER/NAME` lists the pull requests that revision judged.
- **Per-user installation.** `bin/wf-install --channel NAME --key ed25519:…` installs the verified revision once; `--revision HASH` installs a hold; `--prune` removes revisions nothing uses.
- **Owner-merge or `notice`.** Under `approval.checkpoint: notice` the agent merges every pull request once the gates pass and the owner is told. A change to `.github/` is judged by the pull request's own copy, so `wf ci` cannot block it: a `notice` project **needs a host merge gate** that requires an independent review for workflow and enforcement paths. Without one, keep `milestone`.

## Authority by stage

Defaults; the profile may delegate or reserve differently, in writing.

| Stage | Delegated to the agent | Reserved to the owner |
|---|---|---|
| Deployment | Non-production environments the profile names; post-release verification | Production deployment and its credentials; release authority |
| Incidents | Declaring, evidence, the smallest fix, verification, scheduling the review | Ordering a hotfix deployment; rollback; communication to customers or users |
| Maintenance | Cycles within the authorised maintenance milestone and its limits | Renewing the milestone; spending beyond limits; data retention and deletion |
| Upgrades | Preparing the upgrade task and record migration | Adopting the new workflow version; changing an active milestone's version |
