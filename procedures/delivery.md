# Fewer delivery round trips

Keep one coordinator and independent review. Group related edits and checks inside a coherent task; a checklist item is not a new planning or review cycle. One pull request carries one task. For fewer owner stops, an owner-merge project chooses its checkpoint (`approval-evidence.md`, *Owner-merge mode*); in manual mode, signing rounds and milestone rounds do the same for receipts.

## Avoid repeated CI and owner work

Keep the required workflow check running on both PR and main/push events. Use the trusted classifier on the actual before/after commits to skip expensive product steps only when every changed path is planning-only; continue record, workflow and applicable documentation checks. Unknown paths, enforcement, dependencies, code and generation inputs require the relevant full checks. Do not use whole-workflow path exclusions that strand required checks, or optimize only the PR side while every bookkeeping merge repeats the full main suite. Verify the fast path with one records-only and one production change on both events before adopting it. `wf paths --baseline B --candidate C` reports `planning_only`, true only when there are changed paths and every one is planning; run it from the base-pinned validator as `wf-ci.yml` fetches it, with the pull request's base and head, or a push's `before` and `after`. A missing field (an older pin) means run everything.

## A fast lane per task, a full lane per milestone

The owner's decision (MAINT-0027): develop and test locally, push once per task, run the slow checks once when the milestone is ready; the owner's taps are the plan and the acceptance. A project lists its quick commands in `checks.fast` and its slow ones in `checks.full` (`docs/workflow/config.json`); `wf precheck` runs the first locally before the first push (`--full` the second). The task's pull request is opened as a draft: `wf ci (draft)` judges it and writes the verdict to the run's summary but never fails, so a push costs one quiet run. Write the delivery evidence, then `gh pr ready`: that reruns `wf ci`, the run that counts, and the merge waits for it. `wf paths --json`, `wf ci` and `wf lane --baseline B --candidate C` report the lane: `records`; `full` when the change closes a milestone (a milestone record moves to Verified, Accepted or Released), changes an enforcement path or the config's `checks`; else `fast`. A project's CI runs its slow jobs on `full` only (`templates/github/project-ci.yml`), with no schedule; skipped jobs count as passed. Delivery evidence may report a required check `skipped` only when `checks.full_lane` in the trusted branch's config names it and `wf ci` recomputes the lane as `fast`; every other required check needs `passed`. A change to an acceptance test or `tests/acceptance-map.json` is `full` too. A pin from before v2.16.0 reports no lane, which CI reads as `full`.

## Faster CI

A project's own CI wastes minutes in a few known ways. `templates/github/project-ci.yml` is the shape that avoids them, and `wf doctor` warns (never fails) when a workflow of the project, apart from the installed `wf-*.yml`, does one of them.

- **The test database lives in RAM.** Start it in a step: `docker run --tmpfs /var/lib/postgresql … postgres -c fsync=off -c synchronous_commit=off -c full_page_writes=off`. A service container takes no command, so it cannot. The tmpfs covers the folder above the data directory because Postgres 18 keeps its data one level lower. Measured on one project's suites: 35% off the acceptance run, 11% off the database part of the checks.
- **Independent jobs run side by side.** A `needs:` is for data the next job uses: an output, an artifact, a result. A chain without data is the same work in a row. Deploys and jobs in a protected environment wait on purpose.
- **One run per pull request.** `concurrency` keyed by the pull request number, `cancel-in-progress` true for pull requests. Key a push to the trusted branch by its commit, so no deploy is cancelled or dropped.
- **A push to the trusted branch reuses its pull request's result only on an identical tree.** The pull request's checks ran on GitHub's test merge commit; when every job passed, the run leaves that commit's tree SHA as the status `wf-tested-tree` on the head. The push runs `wf reuse --candidate "$GITHUB_SHA" --marker <that status's description, or none>` and skips the product jobs only when its own tree SHA is that tree. A pull request that was behind the trusted branch merges to a different tree, a squash that changed the result does too, and a direct push has no pull request: all run in full. A merge by merge commit or squash of an up-to-date pull request has the same tree, so it reuses. Trust boundary: only this workflow's own token writes the marker. The push reads a `wf-tested-tree` status only when its creator is `github-actions[bot]` and its link is a run of this repository's Actions, and ignores any other (a person's token with `repo:status`, an installed app); give `statuses: write` to the `result` job alone. The post-merge run is the deploy gate, so a forged marker would deploy a tree no run tested: that is why the author is checked. An error from `wf reuse` itself (an older pin, an unreadable marker) means a full run, never a failed one, and a failed API call while writing the marker never fails the required check. Nothing about review or merge rights depends on this.
- **Records-only changes skip the product jobs.** `wf paths` and `wf ci` report `records_only`: at least one path, every one a planning path (the project's `planning` globs, wherever they point) or a milestone or decision record under the records directory, none the config or acceptance definitions (`docs/workflow/config.json`, `docs/workflow/acceptance.json`) or the records directory's profile, none an owner-approved acceptance test. Where the project names owner-approved acceptance tests (`paths.acceptance_tests`), a milestone or task record is never records-only either, because its status decides which mapped tests may fail and so which must run. Unlike `planning_only` it counts milestone and decision records, which are governing by default and hold no code; `wf next`'s baseline walk (`readiness.md`) uses the same definition. A missing field (an older pin) means run everything.
- **Deploy jobs always run.** Reuse and records-only skip tests, never a deploy; the deploy depends on the one required `result` job, not on the skip decision.
- **Runner labels stay `wf-build` and `wf-gate`.** A project depends on those two only, through `CI_BUILD` and `WF_GATE`. On a private repository a job on `ubuntu-latest` costs minutes; `wf doctor` warns, except for a job that holds deployment secrets.

Measure approvals, CI runs and runner-minutes per accepted outcome, including review findings, rework and defects. A smaller PR count is not itself a quality or cost improvement. Use the next comparable task's benchmark in `templates/pilot.md`.
