# Present, accept and release

Before requesting owner acceptance, complete implementer verification, independent review and assembled-candidate verification.

Then, in order:
1. The milestone review of the whole milestone diff (`review.md`).
2. The owner's trial environment, prepared with demo data so every trial step works as written.
3. The trial walk, once the milestone review is back and its fixes are merged: a walk before them is walked again. Run it in the background and carry on meanwhile. Give the `trial-walker` agent (launched with `roles.walker`'s model and effort), or a fresh context with browser automation, the trial steps, how to start the app with demo data, and the profile's languages and screen sizes, on a local build of the candidate. Fix what it finds, or correct the steps, and walk again, rerunning only the steps whose code or wording changed with the walker's kept scripts, until every step passes. Post its screenshots on the acceptance pull request.

A project without a user interface says so instead. An unavailable walk is a blocker.

Prepare `templates/acceptance.md`: candidate revision/build/environment; delivered behaviour and exclusions, with the planned and discovered tasks and work moved to later milestones; access or reproducible demo; scenarios with actions/expected results; persistence/calculations/state-transition evidence; checks/review/resolved findings; issues/unavailable checks; consequential changes; next milestone/prerequisites/proposed limits.

Derive data, access, external services, configuration and operations changes from the actual candidate. Use none only when verified absent, and not verified when evidence is unavailable. Do not include secret values. This summary cannot retroactively authorise reserved choices. Unavailable required technical checks block acceptance presentation. Encode an approved pre-merge condition as a governing decision with `required_before: integrate` (or a deferred `D-NNNN@integrate`), so `wf ci` enforces it; a Draft PR or prose warning is not a gate.

The owner (with two or more `owners`, the milestone's `owner`) tests the product experience and outcomes. Record accepted scenarios, exact candidate, issues and owner decision. Include: **Acceptance is not a declaration that you audited its code or security.** Capture the decision through the owner approval receipt, not an agent-written accepted field. In enforced and owner-merge modes the agent opens one pull request that sets the milestone Accepted and carries the acceptance record (`templates/acceptance.md`) in its description; the owner tries the milestone and merges (or, enforced, approves) it to accept, or says what to change. That merge is the acceptance: `wf ci` always leaves it to the owner, and a checkpoint's hold on the next milestone lifts once it is on the trusted branch. Where the config sets `acceptance_evidence`, that pull request also carries the marked block of `templates/acceptance-evidence.json`: the accepted revision, the milestone review, the walk, everything `wf ci` deferred to this acceptance, and each task's `accepted_findings`. `wf ci` checks it. A workflow upgrade the owner merges during the milestone (the files `bin/wf-upgrade` writes), brought in by merging the trusted branch, leaves the review and walk standing; anything else after them, the project's own code or deploy workflows from the trusted branch included, or a workflow file the pull request changes itself, needs them again.

Use `wf lifecycle --stage accept` to validate recorded technical/integration evidence and acceptance; in manual mode `wf closeout` checks the owner's acceptance receipt for each milestone a round accepts (`approval-evidence.md`, *Closeout*). For a complete milestone, its acceptance record and receipt must contain every milestone scenario; checking only a task does not accept the milestone. Changed experience/outcomes after acceptance require acceptance of the new candidate, and affected technical verification always repeats.

Before release, use `templates/release.md` and `wf lifecycle --stage release`: configuration/secrets/permissions, migrations/compatibility, monitoring/failure visibility, backup/restore/rollback/forward recovery, deployment/support instructions, devices/provisioning/updates, deferred inputs and explicit release authority. Recovery counts as verified only when a rollback has been exercised once and a backup restored once on a non-production target, where applicable. What happens after release is `operate.md`. Document justified not-applicable items. Release the accepted artifact or verify its relationship to the accepted candidate. Keep Implemented, Verified, Accepted and Released distinct. These commands validate evidence; they do not deploy.

Before declaring delivery complete, identify the actual deployed revision/artifact and inspect the latest required main/push checks for that exact revision. Use `wf delivery-check --repository OWNER/REPO --candidate SHA --workflow-file .github/workflows/verify.yml --branch main --required-check JOB` for each required GitHub Actions workflow (repeat `--required-check` for multiple jobs). Save its timestamped result on the PR. Failed, pending, missing or skipped required checks remain unresolved; a green PR run or later bookkeeping commit does not substitute. The command observes CI, not deployment identity, independent review or authority. If a successor is used, verify its relationship to the delivered artifact and document the original failure's disposition. Do not silently broaden retries or label an unexplained failure a flake.
