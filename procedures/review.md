# Independent review and integration

Prepare a committed candidate plus scope, task/milestone records, governing requirements and acceptance definitions, relevant designs, exact base/candidate diff, verification evidence and limitations. Use `wf review-packet --baseline SHA --candidate SHA --task T-NNNN --evidence /external/checks.log` to prepare fixed canonical references from a clean checkout, and rerun it after review to detect changes. It grants no approval. Launch a separate review context without the implementer's conversation or informal reasoning: a harness subagent with an explicitly empty starting context or a fresh session. For Codex, set `fork_turns: "none"` explicitly; omission inherits conversation in some harness versions. For Claude Code use a fresh reviewer context, never resume the implementation collaborator. Record the actual launch options/context metadata and candidate SHA with the returned review. A separate agent ID or a `separate_context` assertion alone does not establish independence. The coordinator's prompt names the candidate revision, diff base, task and milestone records, governing requirements, acceptance definitions, designs, verification evidence and limitations, by path or revision, and asks for `templates/review.md` filled in with findings, severity and disposition. It does not paste the coordinator's own conclusions. In Claude Code the `independent-reviewer` subagent that `wf-adopt` installs at `.claude/agents/independent-reviewer.md` is that context; in Codex or Cursor register the same prompt as a custom agent before first use and record it in the toolbox. The reviewer has shell access to run the checks; its instruction not to modify the candidate is a prompt, not an enforcement, so review a committed revision and compare it afterwards. The owner does not run reviews; the owner sees the posted result. Canonical design rationale remains available.

Run the reviewer in the foreground and collect its result in the same turn. A coordinator never ends its turn waiting for a reviewer or other work it started in the background: a harness may not resume it when that work finishes, and the owner becomes the watchdog. A review of fixes is a new fresh-context reviewer given the earlier review and the fix diff, never the earlier reviewer resumed, which keeps its own history and may run in the background. If a reviewer ends in an API or transport error, relaunch it once; after a second failure record the review as missing and stop at the gate.

Review scope, correctness, maintainability, security, regression risk and test fidelity. Look for the failure patterns most often missed in agent-written code: errors caught and silenced, fallbacks that hide a failed call, dependencies added that are unused or do not exist, logic duplicated where the codebase already has it, behaviour beyond the task's scope, tests weakened to pass, a change that crosses a component boundary or breaks a convention the profile's *Technical context* records, and secrets or environment-specific values in code. When a finding category recurs, turn it into a mechanical check (a lint or boundary rule, a test) through a normal task and add it to `required_checks`, instead of relying on review to catch it again; when approving that profile change, the owner adds it to the ruleset's required status checks (setup step 5). Inspect supporting helpers, fixtures, setup, assertions, execution configuration and untagged tests. Mapping IDs prove traceability, not quality. Post candidate identity, reviewer/context, checks, findings with category/severity/disposition, the owner summary, evidence and limits on the pull request using `templates/review.md`. Collect the actual separate-context result; the implementer cannot substitute `reviewed: true`.

New tests for approved behaviour are normal implementation. Explain meaningful test refactors. Correct tests contradicting approved requirements by citing the requirement and independently checking the correction. Approved behaviour changes need a focused requirement/decision approval present on the authoritative baseline first. Removed/disabled/weakened required coverage blocks integration until justified through the correct route; a linked spec PR or candidate approved field is insufficient.

For a renamed required test, place its exact old/new mapping pair, current task ID and governing requirement in the authoritative baseline's `docs/workflow/acceptance.json` `mapping_migrations` before relying on it. The candidate's own declaration grants nothing. Confirm the replacement still tests the approved behaviour, that no unrelated mapping was removed, and that the new test ran once and passed; in enforced mode, record execution and coverage as unverified by the validator; the agents remain responsible for checking them. The validator checks exact traceability, not semantic equivalence. All test code changes require semantic review; the adverse cases in `validator/test/acceptance.test.js` guard the migration boundary.

After review, assemble the candidate with the latest authoritative baseline and rerun required integration checks. Revalidate approval, readiness, paths, coverage and review at that exact candidate. Capture verification/execution and review through the owner-controlled receipt procedure. Keep candidate code in a separate unprivileged environment. Invoke the external trusted validator with explicit baseline/candidate; never execute a candidate-selected validator or accept a check name as proof of provenance.

Planning, checkpoints and feedback remain possible while production is blocked. Generated outputs conservatively receive production gates. Protected governing/enforcement changes need scoped signed receipts; dependent implementation still reads requirements/decisions from the earlier approved baseline, so a combined proposal does not approve itself.
