# Coordinate, implement and hand off

## Coordinate and delegate

Start every session with `wf next` (in manual mode with the trust options) and do the action it names, reading what it names; the records, not the session, carry the milestone. Hand the claimed task to a fresh helper agent (an empty-context subagent, run in the foreground) with the task ID, what `wf next` names and the limits. Keep its result, check its commits, run the gates and launch the independent review yourself, then run `wf next` again. The coordinator's history grows by results, not by every file and log a task read. The helper's model counts as the implementer's model in `review.md`. The owner steps in only where the approval route needs them, and never runs technical checks or reviews.

Use one coordinator per authorised milestone (one per person in a shared project, `shared.md`) and one independent reviewer. Check actual Git and external state against `wf next`, and claim the task before work: the claim is its branch and pull request (`wf status --pull-requests`). This is not an unattended distributed lock. Extra workers need separately assigned tasks, worktrees, agreed shared contracts and bounded, separable work worth their coordination cost; they do not shorten serial gates, so estimate the critical path, required checks and owner availability before promising completion. A helper taking one task at a time works in the coordinator's place, not alongside it. Routine commands, reruns and state queries need no other agent.

Delegates receive canonical paths and revisions, scope and limits, never the coordinator's conversation or reasoning; record the harness feature and version in the profile's *Execution*. They return results, findings, tested revision, limitations and evidence links for the coordinator to post on the pull request. They inherit authority, never permission to resolve reserved decisions, publish, sign or approve. Summarise large logs mechanically before loading excerpts. Before repeating work, name the changed input, unresolved finding or distinct gate. Preserve baseline, implementer, independent-review and assembled-candidate verification; reuse never substitutes evidence from another revision or stage. Wait for an event or back off within limits; one coordinator owns a wait, and no agent is launched to poll. Never end a turn while work you started runs in the background: wait for it, or stop it and record why.

## Implement a task

Load the governing sources and checkpoint; confirm scope, environment and identity; record the baseline; inspect existing components, helpers, scripts and the toolbox; make the smallest coherent change; run meaningful checks and investigate failures; obtain independent review and resolve its findings; post evidence and the next action on the task's pull request. Register a reusable asset only after review.

**Tests.** A production-affecting task ships automated tests for the behaviour it adds or changes, mapped to its acceptance IDs where they exist. Where none is practical, the task record says why and names the manual evidence method before review, and the reviewer checks the reason; a missing test is a review finding. For each new or changed automated acceptance mapping, post one failing run before the change and the passing run after it.

**UI.** Run the app in the profile's authorised test environment, exercise the changed journey and compare its rendering at the relevant devices and viewports with approved examples, checking persistence and permissions as well as appearance. Use dedicated test accounts and data and the tool's supported authentication; never add an auth bypass or work around a tool restriction. On the pull request record revision, environment, account role, actions, expected and observed results and useful screenshots, without secrets. Unavailable required verification is a blocker, not a pass.

**Checks.** Follow project patterns for boundaries, errors, data, dependencies, interfaces and tests, and choose the applicable checks: business and regression, type/build/lint, integration and contract, permissions, input, data exposure and secrets, invariants and negative examples, dependencies and security, migration, concurrency, retry and recovery, performance, accessibility and devices. Report tested revision, environment, results and limits on the pull request; raw output belongs in receipt artifacts, not commits. Repeat affected checks and review after material changes.

**Bug fixes.** Reproduce the failure or keep its evidence, add a regression check where practical, fix within scope and recheck the original symptom; record what could not be reproduced or verified. A documented failing baseline stays valid, and readiness, required checks and review still apply. A production incident follows the hotfix lane in `operate.md`.

## Work found along the way

Work the plan did not include is recorded, never done beyond scope or left only in a handoff. Inside this task's scope and acceptance IDs, do it here and say so on the pull request. Needed for this milestone but outside this task: a Draft task with the same `milestone:`, a body line `Found in T-NNNN: <reason>` and prerequisites for any order, leaving the milestone's `tasks:` as authorised so nothing goes stale and `wf status` marks it discovered. Anything else becomes a Draft task in its later milestone from the profile's *Delivery* list, or a decision record when it changes scope, behaviour or acceptance (POLICY § 5). Tasks stay flat: order is a prerequisite, never a subtask. Number a new record above every ID in the trusted branch's history and in open pull requests.

## Checkpoints and task records

A shared checkpoint is a commit beginning with the task ID; an incomplete condition is stated. Publish only to the authorised location after the route's identity check, and keep genuine human authorship. Read-only findings go in the relevant record when future work needs them, otherwise on the pull request or issue.

In the pull-request modes (enforced, owner-merge), once a production candidate's checks and independent review are done, put the delivery evidence for its head (`templates/delivery-evidence.json`) in the pull request description: the line `<!-- agent-workflow:delivery-evidence@1 -->`, then the JSON in a fenced `json` block. `wf ci` fails a production change without it; editing the description reruns the check, and a new commit needs new evidence. Run `wf ci --delivery-evidence FILE` yourself first. Under owner-merge, merge the pull request yourself only when that reports `merge: agent` and every required check has passed; anything else waits for the owner's merge. When a milestone's last task merges, prepare it for the owner's acceptance and stop (`accept-release.md`).

One pull request carries one task, never one step. Its branch holds the code, the task record's checkpoints and follow-ups and, as its last commit, the record marked Done, which `wf ci` accepts while the trusted branch still has the task Ready or Active; otherwise the coordinator marks it Done in a planning change after the merge, before any task naming it as a prerequisite is assessed (one that completes a scenario with owner-approved tests goes to the owner, so prefer the task's own branch). Batch every other record change into the task's branch or one planning change: the owner reviews what the project protects, not bookkeeping. Marking a task Done records `implemented`, the candidate its receipts name, and keeps `baseline_revision` as the baseline its `wf ci` ran against (in a milestone round, the previous task's Done commit), from which `wf closeout` re-runs the gate. Without pull requests (a local manual-mode project) the task's commits stay on its branch and the trusted branch moves only by the fast-forward `wf closeout` prints once the signed round passes (`approval-evidence.md`, *Closeout*).

Keep Done records until the milestone is accepted, since prerequisites, coverage and the planned and discovered tasks are read from them, then remove them in one records-only change (one completed in a round only after that round has closed, in manual mode in a later round, which needs no signature with derived baselines); the pull requests are the permanent record. A Done task in no milestone may go at once. A record another task still names in `prerequisites` or `governing` stays until that one goes, and `wf ci` fails a change that removes it early or names a missing record; a task in another milestone depends on an approved contract (`contract:`), not on a task.

## Resume, limits and handoff

Before resuming, inspect branch, working tree, claims, logs, pull requests and external actions already taken; never replay side effects from a missing handoff. Track cumulative time, usage, retries and spend against the milestone's approved limits on the task's pull request or handoff (unknown usage is unknown), check what remains before each assisted call, and save progress and stop at a limit. Count retries in the limit's unit: a per-check limit keeps a stable check identity and its cumulative unexpected failures across agents, checkouts and sessions, never pooled with other checks or reset on success; expected test-first failures are recorded apart. Renaming or splitting a failing check grants no allowance. When stopping, cite the check, attempts and limit; correct mistaken accounting with evidence, never erase failures or extend an exhausted allowance.

In manual mode each signing round ends the coordinator's session (`approval-evidence.md`, *Signing rounds*). After signing, a fresh session (a new `claude` or Codex session, not `--continue`, `--resume` or one carried over by `/compact`, whose summary no gate checks) runs `wf closeout` and continues from the records and the handoff. Within one task compaction is acceptable; afterwards rerun `wf next`, check `git status` and `git log`, and trust them over the summary. A session carried across rounds rereads its growing history on every step; in the first measured pilot that was 82% of the cost. Without a pull request or issue, the handoff goes beside the round in the signing drop as `<round>-handoff.md`, never in the checkout.

Every session records one outcome with `templates/session.json` (progress, ready-for-review, verified-complete, blocked, stopped-by-limit or no-progress), written outside the checkout, checked with `wf session` and posted on the pull request or issue; process success or a new commit alone is not progress. Stop affected work on reserved decisions, missing access, exhausted budgets, repeated no-progress or a suspected safeguard failure, and the milestone at owner acceptance; another milestone and release need their own authority. The handoff on the pull request (or issue before one exists) gives changed work, verification and revision, uncertainty and blockers, the next eligible action and **Workflow friction this session: none / report IDs**, reported as `maintenance.md` says, explicit user complaints included; a report never changes readiness. Never commit handoff files.

When manual continuation is needed, supply:

> Resume task T-____ in milestone M-____. Read AGENTS.md and run `wf next`; read what it names. Inspect the latest checkpoint, the handoff on the task's pull request or issue (or beside the round in the signing drop), and actual Git/external state; after a signed round, run `wf closeout` first. Recompute readiness against the freshly fetched authoritative revision. Continue only the next eligible action recorded in the handoff, within remaining limits. Post evidence and an explicit outcome on the pull request or issue; stop at the next reserved decision or acceptance boundary.

## More than one person

When the profile lists two or more `owners`, also follow `shared.md`: who selects and claims work, and how the plan changes.
