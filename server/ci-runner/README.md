# CI runners on the owner's machine (MAINT-0017)

A project's GitHub Actions jobs can run here instead of on GitHub's metered runners. **Private repositories only:** on a public repository, a pull request from a fork could run code on this machine. Each project gets two LXD containers, each registered as a runner for that repository only, under its own label and no default ones:

| Container | Profile | Runs | Has |
|---|---|---|---|
| `<project>-ci` | `ci-build` | the project's tests and deploys | Docker (containers, volumes and networks cleared after every job), sudo for the runner |
| `<project>-gate` | `ci-gate` | the workflow's own jobs: `wf ci`, `wf-status`, the client page | Git and `gh`; no Docker, no sudo |

**What each runner trusts.**
- **The build container** runs whatever any account that can push sends it: a pull request's tests, and the packages they install, run there as root inside the container.
- **The gate** runs `wf ci` only for pull requests into the trusted branch; any other pull request's `wf ci` goes to GitHub's runner. It runs `wf-status` and the client page only on the trusted branch. Each job's first step checks the branch name exactly, because GitHub compares names in expressions ignoring case: a branch called `MAIN` would otherwise pass. The client page's dispatch job also runs there for any pull request, but it only runs a fixed `gh workflow run`. On the gate run:
  - the workflow files;
  - the validator pinned by the trusted branch's `docs/workflow/config.json` (at the pull request's base commit);
  - that branch's `scripts/wf`.

  So code reaches the gate from an account that can change workflow files, or that can get a change onto the trusted branch. A token needs the Workflows permission to change workflow files; an SSH key or the web needs only write access. In enforced mode, code-owner review guards the trusted branch. In owner-merge and manual modes, only the workflow's rules stop an account with write access from merging. **There, the gate is as trustworthy as every account with write access.**
- **Labels are fixed; variables are switches.**
  - The workflow files name the labels: `wf-gate` for the gate and `wf-build` for the build runner.
  - The repository variables `WF_GATE` and `CI_BUILD` only turn them `on`. Any write collaborator can set an Actions variable, so it may switch a runner off, which sends its jobs to GitHub's runner, but never sends a job to the other runner.
  - Changing a label means changing a workflow file.
  - Only the installed wf workflows (`wf ci`, `wf-status` and the client page, from the trusted branch) run on `wf-gate`. A job that runs code from a pull request or its base runs on `wf-build`, however light it is, because the gate label is trusted.
- **The agents' credential** can change neither workflow files nor runners. Use one of:
  - a fine-grained token with Contents and Pull requests (and Issues, if needed) only;
  - a classic token with only the `repo` scope, for an account with write but not admin access. It can also start and re-run workflows; the exact branch checks contain that.

  No Workflows permission or `workflow` scope, no Administration permission, no SSH or deploy key with write access, and no app holding the Workflows permission. Push workflow-file changes (`wf-adopt`'s scaffold, `wf-upgrade`'s refreshes) from a session the owner attends. Keep the repository setting "Run workflows from fork pull requests" off. Before switching `WF_GATE` on, delete or update any branch whose `wf-ci.yml` predates v2.5.1 (v2.5.0's sent every pull request to the gate), and turn on "Automatically delete head branches".
- **Both containers are persistent,** and what a job leaves behind applies to later jobs. Until each job gets a fresh container (MAINT-0017 D1), `wf ci` on the gate is only as trustworthy as the accounts above. A job that holds deployment secrets stays on GitHub's runner. The exception is the client page's deploy job, which holds a short-lived token for that page alone.

**Size them for the host.** `init` creates the profiles and sets only the keys a profile lacks:
- build: 4 CPUs and 6 GiB;
- gate: 1 CPU and 1 GiB.

Change them with `sudo lxc profile set ci-build limits.memory=5GiB`; running `init` again leaves your values. The limits are per container, and they are ceilings, not reservations: each project adds 6 + 1 GiB. Keep the total, plus whatever else runs on the host, within its memory, or a shared peak wakes the host's out-of-memory killer, which can pick the SSH server. Protect remote access from it (`OOMScoreAdjust=` on those services).

**LXD's updates** reload its daemon, and running containers normally carry on; restarting LXD itself (`snap restart lxd`) stops them. To keep updates out of working hours anyway, give snapd a refresh window, `sudo snap set system refresh.timer=04:00-05:00` (it applies to every snap), or hold LXD with `sudo snap refresh --hold lxd` and update it by hand.

## Once per host (Ubuntu with snapd, and ufw active)

```bash
bash install-host.sh
```

It stops if ufw isn't active, since the firewall rules would then protect nothing. It also makes LXD's daemon start at every boot. The snap otherwise starts it only on demand, and after a power cut it left the containers stopped. `create` sets `boot.autostart` on each container itself; running it again on an existing container repairs one made by an older release. It keeps the containers out of the LAN (`CI_LAN`, default 192.168.0.0/16).

## Once per project

```bash
sudo ci-runner create shop-ci build
sudo ci-runner create shop-gate gate
sudo ci-runner register OWNER/shop shop-ci shop-gate
```

`register` first checks that GitHub doesn't show the repository publicly. Then it asks once, hidden, for the registration token from the repository's *Settings → Actions → Runners → New self-hosted runner* (only an admin of the repository can make one). Each runner is registered under its role's label, taken from its container: `wf-build` or `wf-gate`.

Then, in *Settings → Secrets and variables → Actions → Variables*, set `CI_BUILD` = `on` and `WF_GATE` = `on`. The project's own CI uses `runs-on: ${{ vars.CI_BUILD == 'on' && 'wf-build' || 'ubuntu-latest' }}` for its product jobs; the installed workflow files read `WF_GATE`. `templates/github/project-ci.yml` is a project CI in that shape: parallel jobs, the database in RAM, one run per pull request, and a push that reuses its pull request's result on an identical tree (`procedures/delivery.md`, *Faster CI*).

Runners registered by v2.5.0 under other labels need these labels added (*Settings → Actions → Runners →* the runner *→* labels, an admin's step), or registering again.

## When a runner is down

Jobs queue for it rather than fail, so merges stall. Cancel the waiting run, set its switch (`CI_BUILD` or `WF_GATE`) to anything but `on` to send those jobs to GitHub, then push again, or edit the pull request's description to rerun `wf ci`. A runner that has been offline for 14 days must be registered again (`register`). `sudo ci-runner status` lists the containers and their runner services.

## The pool: a fresh container for every job (MAINT-0017 D1)

`ci-pool` replaces the two persistent containers per project with containers that live for one job. A project's `runs-on` lines do not change: the pool serves the same labels, `wf-build` and `wf-gate`. It is a root service on the host, one Python file with no dependencies.

Every 15 s or more (see the API budget below), for each repository on its list, it asks the **job source** for queued jobs. For a job whose label it serves, it asks the **JIT source** for a runner config that allows exactly one job, puts it into a container made from the label's image, and starts the container. The runner takes its job, exits, and the container powers off; the pool deletes it. Nothing is reused, so what a job leaves behind never reaches the next one.

- **Where jobs and tokens come from is a contract** (`ci-pool.contract.md`, v1), two commands in the config. `ci-pool-github` is the reference: a GitHub token in a root-only file (`/etc/ci-pool/github-token`, mode 0600 or tighter). A host that keeps its credentials elsewhere replaces the two commands and nothing else.
- **The token's permission, and its risk.** Creating a repository's just-in-time runners and deleting its runners needs the repository permission **Administration: write** (fine-grained token or GitHub App; plus **Actions: read** to list runs and jobs). GitHub has no narrower one for this. That permission also changes rulesets, branch protection and repository settings, so root on the host, or anyone who reads `/etc/ci-pool/github-token`, can lift the merge gate. Treat the file like a deploy key: root-only, never copied. Prefer a **GitHub App** installed on the listed repositories only, with a **short-lived installation token** (one hour) that a timer on the host renews into the file, over a personal token that lives until someone revokes it; with a personal token, use one per repository and an expiry date.
- **API budget.** Per repository and pass the source makes a few fixed calls (the repository, four run listings: queued, in progress, waiting, pending; and, while the repository has containers, the runs in progress again; `api_calls_per_repo_poll` 6 covers them) plus one jobs listing per unfinished run in each listing that finds it, so a run in progress is listed twice while its repository has containers. With `ci-pool-github`, two repositories with one run in progress each and containers cost about 16 calls a pass (8 each); at the 29 s pause the fixed estimate gives two repositories that would be about 2,000 calls an hour against the 1,500 aimed for, so the reported count stretches the pause to 39 s (about 1,480 an hour; `ci-pool-github` lists `pending` runs too, as home's broker does, which is one of the fixed calls). One token has 5,000 calls an hour, shared with everything else it does. The pool therefore never polls faster than `ceil(repositories × api_calls_per_repo_poll × 3600 / api_calls_per_hour)` seconds (the fixed estimate), nor faster than `ceil(the last pass's reported calls × 3600 / api_calls_per_hour)` (capped at 300 s), with at least `poll_seconds` and 15 s. The reported count is the `api_calls` a source puts in each answer (`ci-pool.contract.md`); `ci-pool-github` reports every call an answer made; a failed answer (an HTTP error, a rate limit) reports nothing, so that pass counts at the fixed estimate. With the defaults (6 and 1,500 an hour) and a quiet source, 1 repository polls every 15 s, 5 every 72 s, 10 every 144 s; a pass that cost 16 calls stretches the next pause to 39 s. JIT `create` and `remove` (one call per job) are outside the budget. The effective pause at start is in the `started` event.
- **Containers are launched by count, not by job id.** A runner takes any queued job with its label, not necessarily the job that made the pool start it. So for each repository and label the pool starts a container while queued jobs outnumber the containers whose runner has no job yet, up to the cap. A job's id names its container and is remembered (in the state file, before the container starts) only to keep a launch from repeating while that container lives, during its 2-minute retry pause after a failed launch, or for 10 s after it ended (a lagging listing). Queued jobs of a run that is already in progress are found too, as are `needs:` jobs once they are queued. A launch a crash left without a container is closed on the next pass and the job launched again.
- **Never kills a running job for room.** A container is deleted only when its runner has exited, after the hard timeout (2 h), or when no job was assigned to its runner within 5 min (the job was cancelled, or another runner took it). Unassigned means both: GitHub's running list does not name the runner, and no `Runner.Worker` process (the runner starts one per job) runs in its container. The list can miss a job that is running (I-121: unregistering such a runner made GitHub cancel the step, `UserCancelled`), so past the 5 min the pool looks inside (`ps -e -o comm=`, 10 s, 64 KiB); a Worker holds the container (`assigned_by_worker`, logged once), and a check that fails holds it too (`worker_check_failed`, each pass). The runner is then unregistered first, and if GitHub refuses (it still holds a job) the container stays. The hard timeout does not look inside. Assignment is checked on every pass, so a container that came back after a host reboot without its JIT config stops holding a cap slot. If the job source does not answer, nothing is deleted.
- **Caps and admission.** Per label `cap` (start with 1 build and 2 gates). A container starts only while the label is under its cap, `MemAvailable` is at least 3 GiB, CPU pressure (`some`, avg60) is under 40 and memory pressure under 10; the check repeats at every start, with the memory limits of containers started in the last minute (this pass included) already taken off `MemAvailable`, since they have not used it yet. A missing reading refuses. A label may carry its own `admission` (the same three keys, overlaid on the global ones); the example gives `wf-gate` `"max_cpu_psi_avg60": 100`, which means CPU pressure does not hold gate jobs (the installed wf workflows need git and node, no Docker) while the memory rules still apply. The 100 rule is for CPU only: `max_mem_psi_avg60` keeps `>=` at every value, so a memory pressure reading of exactly 100 still refuses. Only the installed wf workflows (`wf ci`, `wf-status` and the client page) run on `wf-gate`; a job that runs code from a pull request or its base runs on `wf-build`, however light it is. A refusal holds only its label for the rest of the pass, in every repository; the others still try. `ci-pool check-config --config FILE` validates a config without touching `lxc` (exit 0, or 2 with the reason). Containers have a hard memory limit and no swap.
- **A stopped spare per label** (`pool-<label>-spare`) is made from the image and not started, so it uses no memory; a job renames it, starts it, and a new spare is made. A spare of an older image is replaced.
- **Containers are `pool-<label>-<job id>`;** runners are `ci-pool-<label>-<last 8 of the job id>`. Each event is one JSON line on stdout (journald). The `deleted` event carries the job container's `memory_peak_mib` (cgroup `memory.peak`, MiB) and `oom_kill` (from `memory.events`), the highest the pool read from `/sys/fs/cgroup/lxc.payload.<name>/` on its passes and just before the delete; a container that stopped on its own has no cgroup left, so a peak in the job's last pause can be missed, and a container never read, or one the pool has no record of (an orphan), gives `null`.
- **The runner's diagnostic log is kept when the pool deletes a container as `unassigned` or at the hard timeout (I-121).** A job cancelled mid-step can leave its runner's container running with no job assigned; the delete used to take the runner's `_diag` log with it, and that log names the signal or the lost Worker. Before the delete the pool copies the newest `*.log` files of `/opt/actions-runner/_diag` (the last 2 MiB of each, at most 10), the container's `memory.events` and `memory.peak`, its process list (`ps.txt`: pid, parent, process group, session, user, state, start, command name without arguments; 64 KiB), the journal of `ci-pool-runner.service` alone (`journal-runner.txt`: the last 100 lines; whether systemd stopped the unit and why) and the end of its whole journal for this boot (`journal.txt`: the last 400 lines; each journal 256 KiB at most) to `/var/log/ci-pool/diag/<job id>/` (root only: 0700/0600) and logs `diag_kept` with the path; read them with `sudo ls /var/log/ci-pool/diag/<job id>`. Only `*.log` names (regular files with one link) are taken, read inside the container as the user that owns `_diag`, never as root; the allowlist filters names only: job code runs as that user and writes `_diag`, so treat the copies as untrusted data. `ps` and `journalctl` run as root inside the container (journald's files are root's); their output is untrusted text too. Before writing it the pool removes, on `sudo`'s journal lines, the command `sudo` logged (everything after `COMMAND=` or `(command continued)`), then the value after `--jitconfig` and any run of 200 or more base64 characters; `ps` prints no arguments. Nothing else is removed: anything a job printed to the journal stays as printed, so these files may still hold a job's output, secrets included, and are root only like the rest. The pool makes `diag_dir` itself (0700) and never changes an existing one: an existing directory that is not root's with mode 0700 is refused (`diag_failed`, `step: diag_dir`), `check-config` refuses `/` and shared system directories such as `/var/log`, and retention removes only job directories holding the pool's `meta.json`. The directory keeps the last 50 jobs or 200 MB, whichever is less; a copy that fails is logged as `diag_failed` and never holds up the delete. All copies of one pass get 45 s together (`diag_pass_budget_seconds`; past it a container is deleted without a copy, `step: budget`), and after SIGTERM no new copy starts, so a stop stays well inside the unit's 90 s stop timeout. Config keys `diag_dir` (`""` = off), `diag_runner_dir`, `diag_max_files`, `diag_max_file_kb`, `diag_max_jobs`, `diag_max_mb`, `diag_timeout_seconds`, `diag_pass_budget_seconds`; the contract (`ci-pool.contract.md`) has the details. A host reinstalls the pool (`install-host.sh`) to take it; no image rebuild.
- **Private repositories only:** the pool ignores a repository the source does not report as private, and any repository not on its list.
- **Only the trusted accounts' runs, checked in the container before the job's first step.** A runner takes any queued job of its label, and a job can be queued after the JIT source last looked (a pull request from a fork, a re-run by someone else). So every pool image has a job-started check, `/opt/ci-hooks/job-started.sh` (written by `ci-pool-image`; `ci-pool-entrypoint` sets `ACTIONS_RUNNER_HOOK_JOB_STARTED` to it and starts no runner without it). The runner runs it after GitHub has given it the job and before any step, job container, service or action. It refuses unless `GITHUB_ACTOR` (who started the run) and `GITHUB_TRIGGERING_ACTOR` (who started this attempt) are both trusted accounts, compared ignoring case, and, when the event payload carries a pull request (`pull_request`, `pull_request_target`, the review and review-comment events, or any payload with a `pull_request`), its `head.repo.full_name` equals its `base.repo.full_name`, as a `workflow_run` payload's `head_repository` must equal its `repository`. An `issue_comment` payload names its pull request only by URL; its workflow runs from the base branch and only the actor check applies. A value that is missing or cannot be read refuses, and so does any error in the check.
  - **Why these values can be trusted.** The runner takes them from GitHub's job message: the actors and the event name from the job's `github` context, the payload, which it writes to `GITHUB_EVENT_PATH`, from the same message. No code of the job has run yet, the container is fresh, and the check and its list are root's. It needs no token: the runner gives a hook none.
  - **The job's `env:` does not reach the check** (actions/runner source). The runner starts a hook with an empty environment of its own (`JobHookProvider.RunHook`) on top of the Worker's process environment, which comes from `ci-pool-entrypoint` through `sudo` and holds nothing of the job. `ScriptHandler` then adds only the variables of the contexts that export themselves (`IEnvironmentContextData`: `github` and `runner`, set last), and the job's `env` context is not one of them. So a workflow cannot hand the check `BASH_ENV`, `BASH_FUNC_*` or `PATH`. A bash script could not defend itself against those, so this is a property the check relies on. The check also calls its external commands by absolute path. To check it on a host after an upgrade of the runner: run a trusted job whose `env:` sets `BASH_FUNC_shown%%: '() { builtin printf LEAKED; }'`; the check's line in the job log must still name the event and the accounts.
  - **A refusal stops the job, not only fails it.** A failed hook fails the job, but the runner still runs every later step whose own `if:` holds, as `always()` does, and a pull request's workflow file is its author's. So after 3 s (the refusal line reaches the live log) the check kills the job's `Runner.Worker`: its parent or its parent's parent, by name and by executable (`/opt/actions-runner/bin*/Runner.Worker`). If it finds none, the pool image's own check (that path, not root) kills every process of the runner's user, which in a one-job container is the runner itself. The job ends with none of its steps run.
  - **The trusted accounts** are `ci-pool-image`'s `TRUSTED_ACTORS` (space-separated logins; the build refuses an empty list or anything that is not a login), written to `/opt/ci-hooks/trusted-actors`. They must be the JIT source's trusted accounts. The default is home's: the accounts its broker's `repo_shared` check trusts (the owner, the agent and the executor App's bot). A host whose accounts differ builds with `sudo TRUSTED_ACTORS='...' ci-pool-image build wf-build` (and `wf-gate`), or the check refuses every job.
  - **Not trusted, so refused on the pool:** `dependabot[bot]` and runs a workflow's own token started (`github-actions[bot]`). Home's broker already mints no runner while such a run is active; these jobs must run on GitHub's runner. The persistent runners (`ci-runner`) have no such check.
- **Unprivileged.** The profiles `ci-pool-build` and `ci-pool-gate` set `security.privileged=false` and nothing that widens it: no `raw.lxc`, no `raw.idmap`, no devices but a root disk on the storage pool `ci` and a NIC on `lxdbr0`; build adds nesting and the mknod and setxattr intercepts for Docker. `ci-pool check-profiles` (also run at start) refuses a profile with any other key, device or value. The firewall rule from `install-host.sh` stops the containers reaching the host itself, except DNS and DHCP.

### Set up (admin, once per host)

1. `bash install-host.sh` installs the files, the firewall rule and the unit `ci-pool.service`, **disabled** (it will not start without `/etc/ci-pool/config.json`).
   The unit creates `/tmp/snap-private-tmp` in its private `/tmp` before it starts: without it every `/snap/bin/lxc` call makes snapd rebuild all security profiles (I-103).
2. Create the storage pool `ci` (btrfs or zfs, so a container starts as a copy-on-write clone in seconds): `sudo lxc storage create ci btrfs size=60GiB`. Then re-run `install-host.sh`: it creates the two profiles where they are missing (and never overwrites ones a host tuned), or `lxc profile create` and `lxc profile edit` them from `ci-pool-build.yaml` and `ci-pool-gate.yaml`. Profiles must say `boot.autostart: "false"` (after a reboot LXD would otherwise bring job containers back without their one-time config); on a host that made them earlier: `sudo lxc profile set ci-pool-build boot.autostart false`, and the same for `ci-pool-gate`.
3. `sudo ci-pool-image build wf-build` and `sudo ci-pool-image build wf-gate`: Ubuntu 24.04 with the runner (checked against its published checksum), git, gh and Node; build adds Docker, Playwright's browsers and `postgres:18.6` pulled, and `/tmp` as tmpfs (2 GiB, counts against the container's memory). The image it replaces stays as `<alias>-prev` for rollback; the one before that is deleted, so rebuilds do not fill the disk. Rebuild on release. This repository installs no schedule for it: a host that wants images newer than its last release adds its own timer.
   **No rsyslog in a CI container.** `ci-pool-image` and `runner-setup` purge `rsyslog`: nothing in a job reads `/var/log/syslog` (containers log to journald), and the ubuntu:24.04 image's `rsyslogd` AppArmor profile denies journald's send to `/run/systemd/journal/dev-log`, about 6,700 denials a day on the host (I-104). A pool image takes the change at its next build; a persistent runner at its next `ci-runner register` (best effort: a failed purge is said and the registration goes on), or now with `lxc exec <runner> -- apt-get purge -y rsyslog`.
   **No apt activity in a pool container, no `needrestart` in any CI container (I-121's second cause).** `ci-pool-image` disables and masks `apt-daily.timer`, `apt-daily-upgrade.timer` and their services, mask PackageKit (`packagekit.service`, `packagekit-offline-update.service`; `software-properties-common` depends on the package, so it stays installed) and purge `unattended-upgrades` and `needrestart`. A fresh container has missed the Persistent `apt-daily-upgrade.timer`, so it fires up to an hour after boot, into any long job; `unattended-upgrades` upgrades packages, and `needrestart`'s apt hook, automatic where there is no terminal, reexecutes systemd and restarts every service on an old library, `ci-pool-runner.service` with them: the runner logs `UserCancelled` and the job ends Canceled (mateen-systems job 127825161221). `needrestart` goes too because a job's own `sudo apt-get install` runs the same hook. **So a pool container takes no updates of its own:** the build ends in `apt-get full-upgrade`, before the second purge, so a pool image's packages are as new as its build. **`runner-setup` purges `needrestart` only:** a long-lived runner keeps `unattended-upgrades` and the apt timers, so it keeps its security updates. The two differ because a pool container lives under two hours (`hard_timeout_seconds`) and is replaced from a current image, and a long-lived runner is not; the cancel of 2026-11-06 was seen in a pool container. Not measured: whether, without `needrestart`, the systemd re-exec of an upgrade on a long-lived runner stops the runner; nothing has shown that it does. **The bigger gap:** nothing rebuilds a pool image on a schedule, so "as new as its build" is only as good as the last build (step 3). A pool image takes the change at its next build; a persistent runner at its next `ci-runner register` (best effort: a failed purge is said and the registration goes on; a dpkg lock is waited for, 5 minutes), or now, while it is idle, with `lxc exec <runner> --env DEBIAN_FRONTEND=noninteractive -- apt-get -o DPkg::Lock::Timeout=300 purge -y needrestart`.
4. `sudo cp /usr/local/share/ci-runner/ci-pool.config.example.json /etc/ci-pool/config.json`, list the repositories, put the token in `/etc/ci-pool/github-token` (`chmod 600`), check with `sudo ci-pool check-profiles`, then **check that `lxc` works under systemd's sandbox before enabling**: `sudo systemd-run --wait --pipe /snap/bin/lxc list` must print the instances (the unit sets no `ProtectHome` and no `NoNewPrivileges`, because `snap run` fails under either: add them to the command as `-p ProtectHome=true -p NoNewPrivileges=true` to see it fail). Then `sudo systemctl enable --now ci-pool` and `journalctl -u ci-pool -f`.

Moving a project: add it to `repos`, wait for its persistent runners to be idle, then remove them. The pool and a persistent runner with the same label share the queue until then. Stopping the service leaves running containers alone.
