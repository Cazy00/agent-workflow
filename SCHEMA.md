# Record formats and mechanical gates

This describes the validator at this revision. `POLICY.md` governs if a mechanical rule or procedure conflicts with the policy. Record a workflow defect rather than bypassing a gate. Three approval modes exist. In `enforced` mode, setup verified GitHub protection, code-owner review and a worker account (by `bin/wf-protect` read-back or the approval-path test) and recorded the label in the baseline's config and profile; the immutable authoritative baseline is then the approved baseline and receipt-dependent technical checks report `unverified` items for the agents to substantiate on the pull request; owner approval is not a code audit; supplying the trust options runs the full receipt gate instead. `owner-merge` mode is checked the same way but stands for the owner's own merge, which nothing protects or proves: every `unverified` item names that route and the mode, and routine delegation refuses it. In `manual` mode, explicit signed receipts are required and nothing is inferred from branch contents.

## Records and sources

Records use Markdown with a leading and closing `---`; one `key: value` per line. Values are scalar strings or `[a, b]` lists; empty values are unset. No multiline YAML. Duplicate keys are rejected. Comments beginning with `#` are ignored. Task, decision, feedback and milestone IDs must match their filename stem.

Config is fixed at `docs/workflow/config.json` on the explicit baseline. `records_dir` defaults to `docs/workflow`. Relative source paths cannot escape a directory root or traverse symlinks. Git sources resolve symbolic refs once to full commit hashes. Change enumeration checks Git failures, uses NUL-delimited paths, and disables rename collapsing so a deleted production path cannot disappear into a planning rename.

| Record | Location / identifier |
|---|---|
| Profile | `profile.md`, governing alias `PROFILE` |
| Task | `tasks/T-0001.md` |
| Decision | `decisions/D-0001.md` |
| Milestone | `milestones/M-0001.md` |
| Feedback | `feedback/inbox/F-0001.md` |
| Acceptance definitions | Fixed `docs/workflow/acceptance.json`, IDs such as `AC-001-1` |
| Test mappings | Fixed `tests/acceptance-map.json` |
| Design, review, acceptance, release, setup, pilot, maintenance | Stable project-selected locations recorded in governing/task records |
| Session | JSON run record validated explicitly with `wf session --record` |

The last group has complete human-facing templates/procedures; the record parser does not claim to validate their prose semantically. Approval/evidence receipts enforce the consequential stage claims described below. `docs/workflow/inbox/` holds raw owner input awaiting triage (`procedures/readiness.md`); the loader ignores it, it classifies as planning, and nothing in it carries authority.

## Basic schema

**Profile:** `record: profile`, project, workflow_version, approval_mechanism, approval_label (`manual`, `owner-merge` or `enforced`), coordinator, setup_budget_days. Implementation additionally needs `readiness: Ready` on the approved baseline. Define `required_checks` and `permitted_assumptions` as lists. Readiness fails while `required_checks` is empty: the validator checks records, not code, so the project's checks are the only code gate. Optional `owners` lists two or more people who share the owner role (GitHub usernames); `wf records` and `wf ci` then require every task's and milestone's `owner` to be one of them. The body covers every policy §2 area, source authority and relevant unknowns.

**Task:** `record: task`, id, title, status (`Draft`, `Ready`, `Active`, `Blocked`, `Done`), owner, objective. Owner is the implementer identity a manual-mode review receipt's `implementer` must equal; with `owners`, the person whose agents implement the task. A Blocked task requires resume_condition. Deferred entries look like `D-0001@verify`. Baseline result is `pass` or `fail: summary`.

Production readiness additionally needs nonempty scope, milestone, governing, acceptance, branch, start_revision, governing_baseline_revision, feature_readiness, verification, and review. Scope is a list of path prefixes. Feature_readiness is an approved source path. Optional feature identifies feature-scoped decisions; risks is a list; consequential risks require design. Requirements govern decisions, assumptions, prerequisites and required-before stages. `baseline_revision` and `baseline_result` describe the actual starting checks, and `baseline_revision` is the baseline the task's `wf ci` runs against (in a milestone round the previous task's Done commit), which `wf closeout` reads with `implemented`; `governing_baseline_revision` records readiness sources separately.

**Milestone:** `record: milestone`, id, outcome, status (`Draft`, `Authorised`, `Active`, `Blocked`, `Verified`, `Accepted`, `Released`), coordinator, scope, governing, acceptance, authority, limits, demonstration, stop_conditions and release_authority. Optional `owner`, required with two or more `owners`, is the person who authorises and accepts it. Optional `tasks` lists the tasks planned before authorisation; a task of the milestone it omits was discovered later. Optional `signing` is `task` (default) or `milestone`, the owner's choice of one signing round per task or one at the milestone's end; no gate reads it. The template also records exclusions, prerequisites, checks/review and cumulative usage. Authorised/Active permits implementation; appropriate later states permit acceptance/release checks. The signed baseline supplies authority, not a candidate status field.

**Decision:** `record: decision`, id, question, type (`decision`, `fact`, `technical`, `assumption`, `deferred`), owner, status (`Open`, `Proposed`, `Resolved`), required_before (`implement`, `verify`, `integrate`, `accept`, `release`, `none`). Optional affects lists task/feature/milestone IDs or `paths:prefix`; supersedes and superseded_by are decision IDs. The body preserves resolution, evidence and rationale at the same location. Unknown required stages are invalid.

**Feedback:** `record: feedback`, id, task, revision, workflow_version, rule, status (`Open`, `Classified`, `Closed`). Body: expected, actual, evidence, impact; optional classification. Filing it grants no authority.

## Approval receipts

The trusted operator supplies `--trust-key FILE --receipts FILE --repository OWNER/REPOSITORY`. The key must be outside the candidate repository; setup establishes the owner's actual key identity. Receipts sign the complete serialized payload with Ed25519 and bind purpose, repository, immutable revision and expiration. Tampered, expired, ambiguous, wrong-key and wrong-purpose receipts fail closed. The external repository identity must match baseline config.

In `enforced` mode (`approval.label` in the baseline config and `approval_label` in the baseline profile, which must agree, with an immutable Git baseline and no trust options) the CLI creates enforced trust (`owner-merge` likewise, labelled unprotected: `protected` is false and items name the owner's own merge): `allows('baseline', rev)` holds only for that exact baseline and `claim()` returns nothing, so lifecycle, acceptance and CI output list receipt-dependent evidence as `unverified` instead of errors. Supplying `--trust-key`, `--receipts` and `--repository` runs the full receipt gate exactly as in manual mode; there is no hybrid. Candidate copies of config and profile never select the mode, `--changed` is still refused, and a directory baseline never receives enforced trust. Because trust is then always present, `ci` requires a committed candidate; local diagnostics use a directory baseline with `--changed`.

`baseline` approval is an explicit owner's approval of that revision's governing records. `governing-change` and `workflow-change` separately enumerate approved candidate paths. `verification`, `review`, `integration`, `acceptance` and `release` receipts carry stage-specific evidence; see `procedures/approval-evidence.md`. No self-declared passed/approved/reviewed field supplies a receipt. `--unsigned-receipts FILE` (manual mode, with the trust options) adds unsigned payloads for a dry run: a signed receipt of the same purpose and revision wins, an ambiguity in either tier supplies nothing, and a result that relied on an unsigned payload carries `authoritative: false` and `provisional` and exits 3. With `approval.derived_baselines: true` in both the config at A and R's own config, where A is the newest baseline receipt in R's history (every other baseline receipt in that history is in A's), `allows('baseline', R)` also holds when every path differing between A and R, classified by both configs, is covered by a receipt at a revision X after A and no later than R with the path unchanged from X to R: a governing-change listing it for governing paths and a workflow-change for enforcement paths; for production or generated paths, verification, review and integration receipts whose checks passed with resolvable evidence and the profiles' required checks among them, whose run passed every mapped test at X once, and whose review names the owner of a Ready, Active or Done task as implementer and a reviewer who owns none, with one such set at a revision with R's production content; either for other planning paths; nothing for task and feedback records. Receipts that do not form one line, an ambiguous receipt at A or R, an unclassified path, a path that could pass for another (a backslash, control, format or default-ignorable character, or whitespace other than a single inner space), a shallow clone, a Git failure or invalid records at R refuse derivation. Every validator Git read (Git 2.31 or later; 2.45.1 or later recommended) ignores replace refs, grafts and the commit-graph, allows no transport and no lazy fetch (only the local `file` clone that builds closeout's and the brief's verified mirror), overrides repository settings that change paths or run programs (hooks included), pins the work tree to the `.git` entry's directory and passes Git a minimal environment; a working-tree comparison (a directory candidate, diagnostics only) ignores dirty submodules and is refused when the clone's own local or worktree config names a filter (the operator's global filters, such as git-lfs, are theirs), and a trusted `ci` refuses a directory candidate before reading it. This implementation does not verify GitHub protection history itself: in enforced mode it takes the label pair on the baseline as the setup record's evidence that steps 5 and 9 were completed, and in manual mode nothing is inferred from branch contents.

## Readiness

Read config, profile, milestone, prerequisite tasks/contracts and decisions from the approved baseline; read the working/candidate task with baseline fallback. Require relevant record schema, profile readiness with a nonempty `required_checks` list, authorised milestone, task context and signed or derived baseline approval. Enforce task scope inside milestone scope and changed production paths inside task scope. Require feature source and a design when the task records shared-contract, synchronisation, money, stock, security, irreversible-data or cross-component risks. Assumptions must occur in the baseline profile's permitted assumptions.

Candidate task edits cannot remove trusted prerequisites, decisions, deferred inputs, governing sources, acceptance IDs or risk classifications, nor change established feature/milestone identity to bypass authority. The stage is the latest of the requested stage and baseline/candidate implemented/verified/accepted states; candidate fields cannot lower it. Stage order is implement, verify, integrate, accept, release. `integrate` represents a real pre-merge condition, distinct from local verification; CI evaluates it. Draft is assessable before promotion; Blocked still reports its resume condition; Done blocks new implementation but permits later-stage evidence checks.

Resolve task prerequisites only when Done on baseline; decision prerequisites require Resolved and not superseded; contract prerequisites require approved source presence. Discover relevant decisions by explicit references and task, feature, milestone or path effects. Apply the same supersession and stage rules through decision/prerequisite/deferred routes. Supersession blocks a decision the task names or whose effects name the task; one reached only through a feature, milestone or path effect is skipped when its superseder is on the baseline and in the task's scope, where it is assessed itself. Later-stage decisions remain pending until due.

Record start and baseline conditions. With Git sources, start_revision and baseline_revision must identify available commits in the candidate history (including authorised milestone branches); governing_baseline_revision must belong to authoritative history. Governing-source changes since the recorded readiness baseline invalidate stale readiness. The workflow pin (config `workflow`, profile `workflow_version`) is excluded: a change to it alone leaves readiness fresh. Reassess from current records rather than trusting an earlier Ready status. Documented failing repair baselines remain allowed.

No blockers gives **Ready**. Decision/deferred blockers whose explicit path scopes do not overlap the declared subset permit **Ready for a bounded subset**. Structural problems and relevant/unscoped blockers give **Needs discovery or resolution**. Subset checks apply to every changed production/generated path.

## Acceptance and evidence

Definitions are `{examples:[{id,requirement,method}]}`. `wf records`, `wf ci` and `wf status` check both files wherever they exist in the revision read: IDs `AC-<digits>-<digits>` without duplicates, known methods, existing requirement paths, mappings to defined IDs with existing files and nonempty names, no duplicate mapping. Methods: automated, human, operational, inspection. Requirements must resolve on baseline. Mappings are `[{acceptance,file,name}]`; files must exist in candidate and IDs must be approved. Existing baseline mappings cannot disappear except through an exact migration approved in the authoritative baseline: optional `mapping_migrations:[{task,from:{acceptance,file,name},to:{acceptance,file,name},requirement}]` in `docs/workflow/acceptance.json`. The source must be in the baseline map, the destination newly mapped in the candidate, both must use the same approved automated acceptance ID, and `requirement` must equal its baseline requirement path. Only the named task, when its acceptance IDs include the migrated ID, may consume the grant. Entries are one-to-one and cannot chain or reverse; malformed, unsafe or unrelated removals fail. Candidate-only grants have no effect. After a migration merges, a retained entry is inert when only its destination is in the baseline map; that destination remains protected by the ordinary comparison. When both source and destination are in the baseline map the entry removes nothing and blocks only its own task's attempt to drop the source. A baseline whose history never held the map, as when a project moves its pin from a release that had none, requires none, while the candidate must still carry it; a map removed from the baseline, or one that cannot be read, still fails. Current task acceptance IDs require their applicable automated coverage; unrelated future definitions do not require premature implementation.

Optional `paths.acceptance_tests` (globs; `tests/acceptance-map.json` and `tests/acceptance/**` in new projects) names owner-approved acceptance tests. Classification keeps a matching path's category and adds `acceptance_test: true`. `ci` then also needs a `governing-change` listing each such changed path, at the candidate or at a revision in the candidate's history where the path had the candidate's content (a signed receipt preferred; an unsigned one makes the result provisional); derivation and the brief ask the same. With the globs set, `wf records` and `ci` (by the baseline's globs) fail, and `status` reports, a map outside them and a mapped file outside them. `ci` fails an acceptance test whose name could pass for another path, and a governing or enforcement path whose name classification had to normalise (a backslash), since a receipt for one file must not approve another. `closeout` also needs, for every acceptance test changed between TIP and END by either config and whatever its category, a `governing-change` listing it at a revision in END's history with END's content; an approved end baseline does not stand in for it. A value that is not an array of strings fails configuration loading.

Signed verification receipts contain execution `{revision,tests:[{file,name,status}]}`. Each mapped test, including a migration destination, must occur exactly once and pass. Missing, skipped, failed, duplicate or stale execution fails in manual mode. In enforced mode execution and semantic coverage review are explicitly unverified by the validator; the agents must still substantiate them. Unknown IDs, unapproved removed mappings and missing test files fail. Existing baseline required mappings remain enforced globally. Different parameterized cases must have distinct full test names.

Semantic review is always required: the checker cannot infer every weakened assertion, helper, fixture, setup or runner change. A justified correction preserving approved behaviour/mapping can proceed with review; changed business acceptance needs its own prior governing approval.

Verification needs candidate-bound check results, environment and raw evidence, plus independent reviewer identity/context, all six review areas and disposition of findings. Review identity must differ from the implementer. Evidence may be a nonempty file in the immutable candidate or raw output in signed receipt artifacts, avoiding circular post-test evidence commits. Integration requires a separate assembled-candidate check receipt. Acceptance adds the owner's accepted scenario IDs. Release adds authority, artifact/candidate relationship and the eight readiness areas. These attestations authenticate a collector's evidence assessment; they do not prove semantics without that assessment.

## Integration and CLI

Optional `planning_frontend` is absent/`null` by default. The experimental adapter contract is `{ "name": "speckit", "compatibility_api": 1, "feature_root": "docs/specs" }`; missing fields, unknown options, names, roots and versions fail configuration loading and classification. Opt-in adds enforcement protection for `.specify/**`, `.agents/**`, `.claude/**`, `.codex/**`, `adapters/**`, `integrations/speckit/**`, `docs/workflow/speckit.lock.json` and `.gitignore`, and governing classification for `docs/specs/**` at the existing precedence below. Configured enforcement/production/generated categories retain priority over governing; executable contracts retain production gates. For adapter-enabled Git candidates, CI also rejects tracked temporary task projections, research/analysis/checklists, recovery files and runtime selectors. Experimental adapter helpers validate installed content and derived projections, but grant no readiness, approval or provider attestation. Directory diagnostics report tracked-file exclusion as unverified. Read `procedures/speckit.md` before adoption; its experimental state is not a tested release claim.

Classification precedence: enforcement, production, generated, governing, planning. Globs support `**`, `*`, `?`, `{a,b}`. Config always comes from baseline. Generated artifacts conservatively receive production gates. Unclassified paths block. Production changes require Ready/Active task state (or Done in the candidate while the baseline still has it Ready or Active, so a task is marked Done in its own pull request), current readiness (at least integrate stage), passing implementation/review/integration evidence and acceptance traceability. Governing/enforcement changes require separate scoped receipts. In enforced mode, evidence and approvals that would come from receipts are listed as `unverified` for the PR evidence/approval route instead of failing the verdict; this is not proof of their truth. Planning-only edits remain possible while implementation is blocked.

Trusted Git integration requires a committed candidate containing the current baseline; `--base`, if given, must equal the authoritative baseline rather than a historical merge base. `--candidate`/`--head` determines both the records read and the actual diff. `--changed` and directory sources are diagnostic fixtures and cannot replace an authoritative diff when trust evidence is supplied. CLI Git failures exit 2 instead of becoming an empty passing diff. An added record whose path any commit in the trusted branch's history held with a different identity (title; question; outcome; task and rule for feedback) fails, since IDs are never reused; a record whose every earlier version had its identity passes as a restoration, with a note; a changed identity on an existing record is noted; a shallow clone exits 2. Readiness reads named task records from the baseline, so a change also fails when it removes a task record that a remaining task names in `prerequisites` or `governing`, or when a task record newly names a task whose record is not in the candidate.

`ci --tasks T-0001,T-0002` enables a bounded batch only when baseline `delivery.batching` records `max_tasks` (2..20), `environment` and `rollback`. All tasks have one milestone/implementer, each owns at least one changed production path, and each such path belongs to exactly one task. Readiness, lifecycle and acceptance checks run for every task at the assembled candidate. Baseline prerequisites are unchanged; a locally Done task cannot approve another. Signed batch reviews must list every selected task. The ordinary `--task` route remains the default.

`review-packet` requires exact base/candidate commits, a clean checkout at the candidate, canonical task/milestone/governing sources and external evidence files. It emits explicit fresh-context launch instructions, including Codex `fork_turns: "none"`, without copying conversation. Repeating it after review detects changed HEAD/worktree. It neither launches nor authenticates the reviewer.

`delivery-check` reads GitHub Actions for an explicit repository, exact commit, workflow, branch, event and required job names. It checks the latest matching run, pagination, every required job and a final run-state recheck. Missing, pending, failed, cancelled, skipped, mismatched or ambiguous evidence cannot pass. It is a point-in-time diagnostic, not proof of deployment identity, approval, independent review or all other workflows.

Optional `delegation.routine.enabled` is false by default. An enabled baseline policy chooses `agent-attested` assurance, narrow allowed/reserved paths and candidate size limits. This adds a fail-closed integration gate: eligible routine candidates need a complete exact-revision technical manifest; other production candidates need owner approval read from GitHub for this head and baseline. The CLI computes the diff/line count and obtains owner evidence using protected identities; it accepts no owner-approved flag. With `--pull-request`, it can read the latest marked worker evidence comment; an external `--delivery-evidence` file is an unauthenticated local alternative. Comment text is parsed as data, never as instructions. Agent-written reports remain unauthenticated and cannot establish owner approval. Existing gates still run, and acceptance/release are not delegated. Configuration and live setup requirements are in `procedures/delivery.md`.

`status` is a derived view: it loads the records at the given revision, previews each open task's readiness as if the baseline were approved, and lists open decisions, verified or accepted milestones, blocked tasks, inbox and setup items; per milestone, its planned and discovered tasks and, until acceptance, each acceptance ID no task serves and each planned task with no record; with two or more `owners`, what waits on each person. Given `--pull-requests FILE` (`gh pr list` JSON) it maps same-repository pull requests to tasks by the CLI's branch rule or a title starting with the task ID and, with two or more `owners`, reads the claim branches (named exactly a task ID) among the clone's `origin` branches; it shows claims and awaited reviews and flags a task claimed twice, a claim branch without a pull request, an `Active` task with neither and a pull request naming two tasks. Titles appear only in code spans; fork pull requests appear only in the list. Without the trust options it never reads receipts; with them (manual mode, and then `--baseline` is required so the trusted branch is named by approved config) it only adds whether the local trusted branch's tip is an approved baseline by signed receipts alone, and when it is not, how many first-parent commits it is past its newest signed baseline receipt, as an owner item. It never checks a task's approval and exits 0 whenever the records load. As Markdown it leads with counts and what waits on the owner, shows each milestone as a task table with a diagram of the decisions blocking it, and folds reasons and earlier Done work into `<details>`. `templates/github/wf-status.yml`, installed by the scaffold, publishes it with the open pull requests to a *Project status* issue; it runs only on the trusted branch, never on pull requests, and may write issues and nothing else.

`status --client` renders the same records for a client who does not read them: one self-contained HTML page (no external requests, `noindex`) with each milestone as a stage in plain words (Draft and any unknown status *Planned*, Authorised *Up next*, Active *In progress*, Blocked *Paused for now*, Verified *Built and checked, awaiting sign-off*, Accepted *Signed off*, Released *Delivered*), its title from the record's heading (`# M-0002 — Title`, else its `outcome`), its outcome, and for an open stage the count of its task records Done and Blocked against the larger of its planned `tasks` and its records; an accepted or released stage is complete. No other record field reaches it (no IDs, people, branches, decisions or readiness reasons); the title, outcome and measure appear as written, so write them for the client. It escapes all record text, exits 0 and grants nothing. The optional config section `client` takes `title` (the page's name; default the profile's `project`) and `exclude` (milestone IDs to leave out); any other key fails configuration loading. `templates/github/wf-client-page.yml`, installed by `wf-adopt --client-page`, publishes it to GitHub Pages, which is public.

`closeout --baseline TIP --candidate END` (manual mode, trust options required) reads a verified mirror of the clone (`git clone --mirror --no-local` into a temporary directory, which re-hashes every object and drops the clone's config, hooks and caches; a failure exits 2), so END must be reachable from a ref. It requires a full clone, TIP approved and the local trusted branch at TIP, END to descend from TIP and validate, END to be an approved baseline and, in a round that changes production or generated content, no record of a task not Done at TIP to be gone at END. The tasks Done at END but not at TIP, grouped by their recorded `baseline_revision` and `implemented` (not `verified`, which would raise the stage their own `ci` judges at), must form one chain: the first group's `baseline_revision` contains TIP, each later one contains the previous group's `implemented`, and each `implemented` is in END's history; `ci` runs for each group at those revisions (a batch when a group holds several). No production or generated path, by TIP's or END's config, may change between TIP and the first gate, between one group's `implemented` and the next group's `baseline_revision`, or after the last `implemented`. Each milestone Accepted or Released at END but not at TIP needs an acceptance receipt after TIP and no later than END with `decision: accepted` and every milestone scenario, and one Released needs a release receipt there whose `candidate_revision` is its own revision. A Git error fails it. It writes nothing; when every step passes on signed receipts, `fast_forward` holds the POSIX-quoted command, with hooks and fsmonitor off, that moves the local trusted branch (`merge --ff-only` when it is checked out, `update-ref` with the old value otherwise or when the clone names its own filters, with a note), and it is null for a dry run; a note names another worktree that has the branch checked out. With the trust options `ci` also notes, without failing, a local trusted branch whose tip is not approved.

`brief --payloads FILE` reads an array of payloads or envelopes (with `--repo`, through a verified mirror as closeout does) and exits 1 when any payload would be rejected on its own content: unknown purpose, missing stage fields, uncovered review areas, unresolved findings, a check not passed, an expired or duplicate purpose/revision and, with `--repo`, a mapped test not run exactly once and passed and, with `--baseline` too, a missing required check of that baseline's profile. It renders Markdown headed by the file's sha256: each payload's purpose, revision, commit subject (with `--repo`) and what the signature attests, then accepted findings, tests not passed, protected paths and acceptance and, with `--repo` and `--baseline`, every path changed between the baseline and the round's end (`--candidate`, or the payloads' latest revision) that no payload covers, judged by category as a derived baseline judges it, and the task records riding along. Payload and repository text appears only inside code spans; paths are shown whole as printable ASCII with every other character, and any space that is not single and inner, escaped. Derivation refuses such paths (`validator/lib/git.js`). It grants nothing.

`attest --baseline TIP --candidate SHA --repository OWNER/REPO --expires-at ISO --out FILE` with `--sandbox LAUNCHER --protect PATH...` or `--unsandboxed` reads `attest` from TIP's config through a verified mirror: `setup` (commands), `checks` (`{name, run, report?: {format: junit|node-test, file}}`, names unique, every profile `required_checks` name among them), `env` (names to pass through; `OWNER_SIGNING_*`, `WF_*`, `GIT_*`, `SSH_AUTH_SOCK` and `GPG_*` are refused) and `timeout_minutes` (1 to 240); unknown fields fail configuration loading, so a sandbox can never come from the repository. It needs `--protect` in both modes, and refuses a candidate that does not contain TIP, an `--out` inside the clone or already present, a launcher inside the clone, a protected path that is missing or a directory this process cannot list (a directory stands for every file under it, at most 500), a launcher that does not run `/bin/cat` on an ordinary file, a protected file that `LAUNCHER /bin/cat -- FILE` reads, or whose read does not end with status 1, no output and a `cat:` error line naming the file (a signal, a timeout or a launcher's own error), and, with `--unsandboxed`, a root process and a protected file this account owns or can open. It clones the mirror, checks out SHA, and runs each command as `LAUNCHER /bin/sh -c COMMAND` in that checkout with `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, the locale and temporary-directory variables, `TERM`, the passed names, `CI=true`, `WF_REPORT_DIR` and `WF_NODE_REPORTER`. A check passes when it exits 0 and its report, if any, is read and lists no failed test; JUnit cases take their file from `file` or else `classname`, and must lie inside the checkout. It writes `[verification, integration]` for SHA with the checks, the logs as `artifacts` (each kept to 200 KiB, head and tail, with the whole log's sha256), the tests as `execution`, and `attested: {tool: "wf attest", baseline, sandbox: {launcher, sha256} | null, protected, setup, started_at, finished_at}`; mode 0600. It exits 0 when every check passed and every test in SHA's map ran once and passed, 1 otherwise (payloads still written; a failed setup writes none) and 2 when it refuses. With `--repo` and `--baseline`, `brief` treats a verification or integration payload without that marker as a problem when the baseline's config has `attest`, and lists each attested one for the owner's judgement. The gates read `attested` nowhere: who ran attest is the owner's knowledge, not a field.

`next [--baseline REV] [--candidate REV] [--pull-requests FILE]` defaults its baseline to the local trusted branch named by the working tree's config (the working tree, with a note to commit it, while the adoption is not on that branch) and its candidate to the working tree, and is a derived view like `status`: it exits 0 whenever the records load and grants nothing. Its first action is the first that applies of: record errors; agent setup steps; tasks Done in the candidate but not in the baseline, unless their milestone sets `signing: milestone` and still has a task not Done (manual mode: close out or stage the round; enforced: the pull request); claim problems; changes requested on the agent's pull requests; Active tasks whose readiness passes (or within their subset), and Active tasks to bring back to readiness; Ready tasks whose readiness passes, then those ready for a subset, leaving out a task with an open pull request or claim branch when pull requests are given; Drafts whose readiness passes; tasks needing discovery other than for an owner's decision; plan gaps; Draft milestones, as one planning action each; agent-resolvable decisions; milestones whose tasks are all Done; the inbox; otherwise stop. Each action names the files to read (a task's record, its milestone, what `governing` names, its design and, with acceptance IDs, the definitions and map) and one procedure, and the commands to run. Tasks are taken milestone by milestone in the order the baseline's record of each milestone lists them in `tasks:` (the candidate's for a milestone not yet on the baseline), then discovered tasks by ID. A selected `--candidate` is kept in the commands it prints. A task whose readiness waits only on an owner's decision is listed as held, never as an action. Commands in manual mode carry the trust options. It also lists up to seven further actions, what waits on the owner and the blocked tasks.

`bin/wf` requires an externally pinned full `WF_VALIDATOR_REV`, extracts its committed validator and verifies the baseline adoption pin. It never fetches/executes a candidate-selected repository or runs changed cache files. The authoritative launcher, environment and result mechanism must be outside candidate control; a copied local script and a familiar CI check name do not provide that trust.

## Session outcomes and supported limits

Session outcomes are progress, ready-for-review, verified-complete, blocked, stopped-by-limit and no-progress. All need next_action and friction. `wf session` takes the repository identity from `--repository` or, without trust options, from the baseline config. A verified-complete outcome whose lifecycle evidence is `unverified` (enforced mode) must link the pull request or issue that carries it, and the session output repeats the `unverified` list. Progress requires a meaningful summary and durable evidence (a committed record, or a link to the task's GitHub pull request or issue); ready-for-review also names the candidate. Verified-complete requires validated readiness, coverage and lifecycle evidence. Blocked identifies prerequisite, impact and responsible party. Stopped-by-limit records limit, usage, checkpoint and evidence. No-progress states failure and why a retry would differ.

Assisted coordinators maintain cumulative budgets and serial task claims; this is not a durable unattended runner. Automated duplicate claims, process cleanup, retry accounting and crash recovery are conditional runner requirements and remain unadopted. Live identity permission/protection tests, agent discovery, product acceptance and observed pilot evidence cannot be replaced by unit tests. All commands return JSON (`status` and `brief` Markdown unless `--json`): exit 0 satisfied, 1 failed/blocked, 2 invalid input/execution error, 3 satisfied only provisionally by unsigned payloads, which is not satisfied.

## Relevant freshness and assisted operations

Git freshness now discovers the governing dependency closure at both the recorded and current baselines: profile/config and relevant acceptance definitions, the task's milestone, feature/design/governing paths, prerequisite tasks/contracts, decisions affecting the task/feature/milestone/path, and supersession links. It compares the union, including newly applicable and removed records, using validated literal Git paths. Acceptance comparison covers the relevant task/milestone IDs and their requirement paths; unrelated new acceptance examples do not alone stale a task. Unrelated milestone/decision edits do not alone stale a task. Operational totals/claims belong outside governing milestone records; milestone authority changes still stale affected tasks.

`report` and `runtime` read an explicit external owner-provisioned operations config, not a candidate-selected adoption config. The expected project, central destination, worker, approved tool versions and workflow pin must match. They keep private state outside the project and never supply lifecycle receipts. The reporter accepts fixed catalog fields only, preflights its actual issue route, persists ambiguous writes, bounds reconciliation and holds unresolved delivery. Runtime records support assisted claims, explicit unknown usage, exposure and survey cadence; they are not an unattended runner or distributed lock. See `procedures/operations.md` for data boundaries, commands, recovery and limits.

`prepare-evidence` converts the supplied Node reporter's completed event stream into a summary and unsigned verification payload. Dirty/stale/truncated/ambiguous streams are rejected; failures and skipped tests do not become passing evidence. Collector authentication, raw process exit, review, integration and owner signing remain required. No other test reporter is implied supported.
